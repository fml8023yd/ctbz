# CTBZ 0.2.0 · 留痕与质疑预演

本文件是本次两项更新的施工依据。版本按 0.2.0 走；用户若改版本号，以下所有 0.2.0 同步改。

## 更新一：留痕与方法沉淀

### 目标

每完成一件事都留下可复查的痕迹。遇到新问题、探索出来的方法，必须写清楚：怎么想的、试了什么、哪里失败、凭什么说现在这套成立、下次什么时候能复用。

### 何时写

- 每个 run 结束前写；失败或放弃的 run 也写，记录负结果。
- 探索性任务必须写完整探索记录。
- 例行小任务写简版，不搞仪式。

### 探索性任务判据

满足任一即标 `exploration=true`：
1. 开始时没有已知解决路径。
2. 第一版方案失败或需要换路。
3. 需要探针、实验、对比才能定位。
4. 结论依赖新的证据而非既有知识。

### 留痕位置

- 项目记录：`.ctbz-record/runs/<runId>/method.md`；沿用现有 `.ctbz-record` 结构时放对应 run 目录。父会话可写记录，不算产出交付物。
- 可复用方法：需要沉淀时追加知识库 `experience`，写明来源 runId、适用范围、前置条件、置信度；不自动升 `confirmed`。
- 交付汇报里给出方法留痕路径。

### 模板

```md
# 方法留痕 · <runId>

## 1. 任务
- 原始请求
- 目标 / 硬约束 / 验收
- exploration: true|false

## 2. 路径
- 采用方案
- 关键决策 + 理由

## 3. 岔路
- 备选方案 / 放弃原因
- 失败尝试 / 证据

## 4. 证据
- 命令、路径、版本、输出摘要
- 哪些证据支持哪个结论

## 5. 可复用方法
- 适用场景
- 前置条件
- 步骤
- 坑
- 验收方法

## 6. 探索记录（exploration=true 时必填）
- 假设
- 探针
- 观察
- 结论 / 被推翻的假设

## 7. 知识沉淀
- experience 条目位置
- 是否 confirmed（只有用户明确确认才 true）
```

### 执行角色

- 执行 Agent 回执必须带 `method`：做了什么、备选、失败、证据。只读角色返回方法观察。
- 父会话汇总成 run 级 `method.md`；内容长时可派 scribe Agent 落盘，父会话只审定。
- 不留痕不算完成；关键结论无留痕时，交付标缺口。

## 更新二：质疑预演

### 目标

交付前先站在用户视角挑战自己：用户拿到结果最可能问什么、怎么反驳、我拿什么证据回应。答不上来的，不许装没看见。

### 必答清单（至少 3 条，最多 5 条）

| # | 用户可能怎么质疑 | 必须准备 |
|---|---|---|
| 1 | 真的解决了吗？还是只做了字面要求？ | 原始问题 → 实际结果 → 用户路径证据 |
| 2 | 为什么是这个方案？为什么不是更简单/更便宜的？ | 方案对比、约束、放弃原因 |
| 3 | 边界和反例会怎样？ | 空输入、大数据、并发、失败模式、测试或探针 |
| 4 | 证据可信吗？你真的跑了吗？ | 命令、输出、版本、独立验收者；区分自审与独立 |
| 5 | 成本、风险、副作用呢？ | 预算、回滚、影响面、未解决项 |

### 规则

- 每条写：用户原话式质疑、回应、证据位置、残余风险。
- 没有证据的质疑：要么补验证，要么标“未验证/缺口”，不能靠话术糊过去。
- 高风险交付（不可逆、外部写入、安全、跨模块）必须由独立 challenger Agent 做一次用户视角攻击；challenger 用 reviewer 权限，不新增 profile 角色。
- 质疑预演记录放 `.ctbz-record/runs/<runId>/challenge.md`，交付汇报给路径。
- 用户提出的新质疑若不在预演清单里，记录下来，回流下一轮方法留痕。

### 与现有规则的关系

- 不替代 E3 验收：E3 验“计划→产物”；质疑预演练“用户→交付”。
- 不替代异议义务：异议义务管未决方案；质疑预演管已交付结果。
- 不替代独立反审：质疑预演可以由班主自己做；高风险才加 challenger。
