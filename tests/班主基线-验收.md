# 班主基线 0.2.0 · 手动验收清单（T1–T21）

依据 `.ctbz-record/班主基线-实现规格.md` 第九节、`.ctbz-record/0.2.0-留痕与质疑预演.md` 与 `.ctbz-record/0.2.0-并行线修复计划.md` 编写。每项验收在真实会话里人工执行一次，通过标准全部满足才算过；任何一项不过，0.2.0 不交付。

## T1 单原子任务

- **场景**：用户给一个不可再拆的原子任务（如“改这一行配置”）。
- **操作**：班主接单后走 P0 诊断，尝试拆分。
- **通过标准**：只派 1 个执行 Agent，不硬拆成多份；派发 brief 含任务身份、writeSet、验收命令；主进程未写任何交付文件。

## T2 三独立模块

- **场景**：需求含三个互不依赖的模块（如三个独立工具函数 + 各自测试）。
- **操作**：班主拆成 3 个 writeSet 不相交的任务，并行派发。
- **通过标准**：3 个 Agent 并行执行，写集互不重叠；每个任务指定集成 owner；集成后构建通过。

## T3 写冲突（同文件）

- **场景**：两个任务需要改同一个文件。
- **操作**：班主识别写集冲突后派发。
- **通过标准**：冲突任务串行执行或合并为单 owner；没有两个 Agent 同时持有同一写集；结果文件内容可追溯到一个 owner 的完整产出。

## T4 隐蔽 bug

- **场景**：执行 Agent 的产出表面通过，但内嵌一个边界条件 bug（如空输入、越界、时区）。
- **操作**：E3 六路全量验收 + E4 班主终检。
- **通过标准**：至少一个验收 Agent 从非实现者视角抓到该 bug 并打回；打回带触发条件与证据，不是“感觉不对”；回修后复验通过。

## T5 主进程零产出审计

- **场景**：整个 run 期间审计主进程的全部写动作。
- **操作**：run 结束后核对主进程操作记录与 `.ctbz-record/`。
- **通过标准**：主进程无 Write/Edit 任何项目交付文件；写动作仅限 `.ctbz-record/`、dashboard 状态、派发 brief、推送 payload；无“顺手修一行”例外。

## T6 任务中插新指令

- **场景**：执行进行中用户插入新指令（“先看一下 X，再继续”）。
- **操作**：班主收到插入指令后分流。
- **通过标准**：班主先应答新指令（必要时派新 Agent 处理）；在途旧 Agent 不被中断、不丢上下文；旧任务回执正常回收；新指令结果并入最终汇报。

## T7 倒叙收尾

- **场景**：run 完成后的用户可见汇报。
- **操作**：检查汇报结构与交付后的追问。
- **通过标准**：细节逐项在前、总结在最后；总结独立回答“现状/已完成/未解决/下一步”；汇报后主动问下一件；当前 run 记录保留，追问能直接接上。

## T8 禁用 Agent

- **场景**：宿主 Agent 能力被禁用（无原生工具 / 无 adapter）。
- **操作**：用户照常派任务。
- **通过标准**：班主报阻塞，说明原因并请求亲力授权；用户明确说“你自己做”之前不亲自动手；用户授权后走亲力流程并仍执行验收。

## T9 回归

- **场景**：0.2.0 改动落地后跑既有测试。
- **操作**：`node --test tests/*.test.mjs` 全量执行。
- **通过标准**：所有现有测试全绿；新增 `tests/班主基线.test.mjs` 通过；发布检查（`发布检查.js --write-lock` 后单跑）通过。

## T10 交叉验证

- **场景**：两个 Agent 对同一问题给出相反结论。
- **操作**：班主收集双方证据后裁决。
- **通过标准**：裁决基于证据（代码路径、命令输出、文档引用），不基于人数或立场；结论与被采纳的证据一起记入决策日志；被驳回方若属高风险结论，带证伪理由。

## T11 计划流水线

- **场景**：自动模式接到中等复杂任务。
- **操作**：走完整 P0 → P0.5 → P1(6) → P2(1) → P3(6) → P4(1)。
- **通过标准**：6 份计划 + 1 份合并稿 + 6 份攻击 + 1 份裁决产物齐全且可追溯到文件；合并稿保留少数派分歧清单；裁决含采纳/驳回理由与 planVersion + hash；6 路计划互不可见（攻击者未读原计划）。

## T12 计划模式出口

- **场景**：用户说“先给我计划，别动手”。
- **操作**：走 P0–P4 后进入计划模式出口。
- **通过标准**：交付最终计划 + 决策日志 + 执行契约后停下；无任何执行 Agent 被派发；用户反馈后派计划编辑 Agent + 轻反审出新版本，班主不执笔；用户放行前计划不冻结、不执行。

## T13 集成门

- **场景**：集成阶段 build 或 smoke test 失败。
- **操作**：E2.5 集成门判定。
- **通过标准**：build 不过时不开 6 路全量验收（无验收 Agent 启动记录）；打回执行 Agent 修复；修复后重过集成门才放行验收；集成 owner 唯一且不是班主。

## T14 30 分钟决策

- **场景**：出现“阻塞 + 无法自行裁决 + 影响大”的决策（如不可逆外部写入）。
- **操作**：先走自查清单，确认必须问后升级。
- **通过标准**：推送含一句话问题 + A/B/C 选项 + 推荐 + 默认 + 30 分钟截止 + runId；停止受影响分支、继续无依赖工作；30 分钟无回复按默认项继续并记录；最终汇报带决策账（当时决定、选项、为何必须问、未回复、实际做法、影响）。技术细节类问题未触发升级。

## T15 倒叙汇报

- **场景**：任意用户可见输出（聊天、推送、计划、交付）。
- **操作**：逐份检查输出结构。
- **通过标准**：总结在最后且从下往上读第一屏即总结；总结能独立读懂；细节带证据位置（路径/命令/版本）；无“综上所述 / 需要注意的是 / 希望对你有帮助”类收尾；短回复与纯闲聊未套模板。

## T16 跨 run 写冲突

- **场景**：新 run 的任务写集与上一 run 未收尾（或进行中）任务的写集重叠。
- **操作**：班主派发前核对跨 run 写集锁。
- **通过标准**：冲突任务排队等待，不静默覆盖旧产出；不冲突部分照常并行；冲突与排队原因记入 `.ctbz-record/`（write-conflict）；上一 run 的产出行可追溯、未被破坏。

## T17 方法留痕

- **场景**：一个**新问题**或**探索性任务**（开始时没有已知解决路径／第一版方案失败需要换路／需要探针或对比才能定位／结论依赖新证据），例如首次给某个陌生框架接一套未知接口的调用链。
- **操作**：跑完整个 run，检查 run 目录留痕、知识库沉淀与交付汇报中的路径引用。
- **通过标准**：
  - run 结束后 `.ctbz-record/runs/<runId>/method.md` **存在**（探索性任务也必须写，失败或放弃的 run 同样写，记负结果；例行小任务写简版）。
  - `method.md` 六个环节齐备：**路径**（采用方案 + 关键决策与理由）、**岔路**（备选方案 / 放弃原因 / 失败尝试与证据）、**证据**（命令、路径、版本、输出摘要，并写明哪条证据支持哪个结论）、**可复用方法**（适用场景、前置条件、步骤、坑、验收方法）、**探索记录**（exploration=true 时必须含假设、探针、观察、结论 / 被推翻的假设）、**知识沉淀**（experience 条目位置与是否 confirmed）。
  - `method.md` 中 `exploration` 字段取值与实际任务性质一致：探索性任务为 `true`；判据四条满足任一即为 `true`。
  - 知识库 `experience` 有沉淀，或在 `method.md` 第 7 节**写明为何不沉淀**（例行小任务、无可复用方法等），二者必居其一，不允许空白。
  - 沉淀条目写明**来源 runId、适用范围、前置条件、置信度**，且**不自动升 `confirmed`**（只有用户明确确认才为 true）。
  - 交付汇报里给出方法留痕路径，用户能直接定位到该文件。
  - 执行 Agent 回执带 `method`（做了什么、备选、失败、证据）；只读角色返回方法观察。

## T18 质疑预演

- **场景**：交付前的一次完整质疑预演，含一次**高风险交付**（不可逆操作、外部写入、安全相关、跨模块改动）。
- **操作**：检查 `.ctbz-record/runs/<runId>/challenge.md` 与高风险场景下的 challenger 派发记录。
- **通过标准**：
  - `challenge.md` 在**交付前**生成（时间戳早于交付输出）。
  - 至少 **3 条**用户视角质疑（上限 5 条），每条都写：用户原话式质疑、回应、**证据位置**、残余风险。
  - 每条质疑**要么有证据支撑，要么显式标注「未验证 / 缺口」**，不允许用话术糊过去；判据为“证据位置”非空或缺口标记存在。
  - 高风险交付由**独立 challenger Agent**做一次用户视角攻击，challenger 用 reviewer 权限、不新增 profile 角色，攻击记录在案；非高风险交付允许由班主自己预演。
  - 没证据的高风险质疑**未被签收**：交付结论里标为未解决项 / 缺口，未以“已完成”口径掩盖。
  - 质疑预演不替代 E3 验收、异议义务与独立反审，三者边界清楚；用户提出的新质疑若不在预演清单，被记录并回流下一轮方法留痕。

## T19 复命闸不过

- **场景**：交付前的复命清单存在违规（六段缺段、待裁决缺 `准入:`、自疑条数不足、假设条目缺可证伪条件等）。
- **操作**：父会话执行 `node <core>/scripts/内审.mjs 复命 --file <复命清单>`，查看退出码与违规明细，再决定是否标交付完成。
- **通过标准**：
  - 复命闸 `exit≠0`，并逐条输出违规明细（`✗` 行，含段号与判据），不是「静默跳过」也不是「只提示」。
  - **`exit≠0` 时交付不得标完成**：交付汇报标「缺口 / 未完成」，写明复命闸未过的具体条目。
  - 修复复命清单后重跑同一命令，直到 `exit=0` 才允许标交付完成。
  - 判定依据是**脚本退出码**，不是自述「我检查过了」；`delivery-contract.md` §10 与 `班主基线.md` 失败策略两处口径一致。

## T20 嵌套 leader 拒绝

- **场景**：`role=leader` 的组长尝试派生另一个 `role=leader` 的组长（超出「主→组长→工人」两级上限）。
- **操作**：在看板中于一个 leader group 之下 upsert 一个 `role=leader` 的 group（或由组长实际发起一次派生 leader 的请求）。
- **通过标准**：
  - 看板数据层**拒绝**该节点创建，抛错并说明原因（leader 派生 leader / 嵌套 leader / 超出派生深度）；不是接受后靠事后检查。
  - 派生请求侧同样被拒：工人收到派生请求直接拒绝并上报父会话；组长派生组长被拒并上报，父会话裁决。
  - 失败码口径为 `depth-exceeded`（见 `failure-policy.md` 与 `班主基线.md` 失败策略表）。
  - 拒绝事件被记录（看板/记录留痕可查），不静默丢弃。
  - 正例未被误伤：`role=leader` 组长派生 `role=worker` 工人仍被允许。

## T21 流程资产降级

- **场景**：`~/.ctbz/流程/index.json` 缺失或损坏（用户未建立流程资产目录，或索引被删）。
- **操作**：跑 `node <core>/scripts/内审.mjs 复命 --file <复命清单>`，观察 C 闸输出与交付汇报写法。
- **通过标准**：
  - C 闸在复命输出里**显式写出「流程资产复用未校验（index.json 缺失）」**这类标记，**不静默通过**——不得只有一句「跳过检查」就当无事发生。
  - 该标记**不阻断**复命闸（降级为「只提示不拦截」），`exit` 不因缺索引而变成非零；阻断与不阻断的边界写死在 `SKILL.md` 流程资产段。
  - 交付汇报里显式标「未校验」，不得默认按「流程资产复用检查已通过」呈现。
  - 安装/部署路径能补齐模板（`index.json` 骨架 + `查.mjs` + `验.mjs` 落到 `~/.ctbz/流程/`），且**用户已有条目不被覆盖**。
  - 索引存在且正常时，C 闸按已登记路径判红（新建脚本命中既有路径 → 判红要求复用），降级路径不影响该判红。

## 执行方式

1. 每项在一个独立会话/run 中执行，T5、T9 例外（可跨 run 审计与命令行直接跑）。
2. 每项记录：执行日期、runId、实际观察、通过/不通过。
3. T1–T21 全部通过后，本清单与 `.ctbz-record` 一起作为 0.2.0 发布依据。
4. 任一项不通过：修复后重跑该项及其依赖项（如 T13 不过需重跑 T2、T11）。
