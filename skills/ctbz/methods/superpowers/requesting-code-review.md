# 准备与发起代码评审

先读 [共享契约](../contract.md)。仅 parent 准备材料、调度 reviewer 和落盘；其他角色只返回需要评审的事实。

来源：Superpowers 6.3.0 `skills/requesting-code-review/SKILL.md` 及 code-reviewer 模板。适配：父会话生成工作区快照，只读 reviewer 消费文件，不要求 Git 提交或 shell 回退。

1. 明确此次检查对象：一个实现任务、复杂修复、重大行为改动或最终集成，按影响范围、不可逆性和判断难度确定审查强度。既有计划要求独立评审时按计划执行；普通小任务可由父会话自审并如实说明，用户禁子 Agent 时不创建 reviewer。多人复核须有各自独立检查价值，不为凑人数或轮数增加审查。
2. 核对任务真实工作区与起点，按 [评审证据协议](../references/review-evidence.md) 从该 worktree 生成不可混淆的材料。保存实际 base/head、暂存/未暂存/新增文件、完整内容和摘要。未授权提交时直接审未提交快照，不为凑 SHA commit，不用父工作区的 HEAD 推测任务范围。
3. 需要派发时经 `initialize select` 选择 reviewer，提供 [任务评审模板](../templates/task-review.md)、任务契约、已确认要求、实现报告、验证输出和评审包的绝对 Read 路径。不要给“不得指出某项”“最高只能 Minor”等预判性结论；父会话自审时也核对实际内容与证据。
4. 收回规格与质量两项结论，这不要求两名审查者。意见须提供具体反例、证据或覆盖缺口；缺件由父会话补齐，针对具体测试疑点安排授权 tester 或主会话验证。用 [接收评审](receiving-code-review.md) 核实问题并修复，保留每轮原始意见与处理理由。
5. 改动或集成改变受审内容后生成新材料，按 [复审模板](../templates/re-review.md) 核对受影响部分，保留仍有效的证据。最终结论标注 snapshot 摘要与范围，不能沿用旧通过代表新内容；达到约定验收且无阻塞问题后停止，非必需建议不阻塞交付。

验收：reviewer 不需要 shell 或写权限就能取得全部必要证据；双结论有具体引用，父会话清楚哪些问题阻断验收、哪些缺证据和哪些可延期。
