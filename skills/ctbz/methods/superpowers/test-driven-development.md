# 测试驱动开发

先读 [共享契约](../contract.md)。parent、implementer、debugger、tester 在已有工具和 write-set 内执行。

来源：Superpowers 6.3.0 `skills/test-driven-development/SKILL.md`。适配：代码行为用红绿验证，文案/配置/研究按风险选择检查；不删除已有用户代码，不要求为例外重新审批。

代码新增行为、错误修复及有风险的重构优先使用本方法。先读 [测试质量参考](../references/writing-good-tests.md)，从用户期望的可观察行为设计测试。纯说明修改、机械生成物或可逆低风险配置可用对应静态检查并说明范围；研究采用假设、观测和否定证据，不把研究强制变成代码单测。

1. **RED**：用项目已有工具写最小失败用例，固定输入与手工推导的预期，覆盖目标行为或原始缺陷。运行具体命令，确认是断言因行为缺失而失败；语法错误、依赖缺失或错误环境不能算有效 RED。测试一开始通过时检查是否覆盖了正确的失败条件。
2. **GREEN**：在 write-set 内实现使测试通过的最小改动，修复实际根因，保留输入校验、错误处理和用户明确需求。不夹带额外功能或大范围重构。
3. **验证**：运行该用例与受影响测试，读退出码及完整相关输出。结果仍失败时查原因，不降低断言迁就错误实现；环境失败单独记录。
4. **重构**：必要时去除实际重复、改善名称或复用既有结构，保持行为不变，再运行受影响检查。没有收益时直接结束本轮。
5. **记录**：把 RED/GREEN 命令、cwd、关键输出、最终内容快照及测试覆盖限制交父会话。先前已有实现或无法安全重放失败时如实说明测试是在实现后补的，不删用户成果来伪造测试先行。

测试难写时先缩小目标、明确接口和依赖副作用。需要大量 mock 才能断言通常应重新检查接口或使用隔离集成测试；需要真实计费服务但没有授权时用可解释的隔离证据并标明限制。

验收：检查确实能发现所针对的错误，最终行为通过，相关回归未失败。验证结论与所测内容一致，不能用覆盖率或“每函数一个测试”代替行为证据。
