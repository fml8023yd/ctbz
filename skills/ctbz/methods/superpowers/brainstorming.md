# 讨论与设计

先读 [共享契约](../contract.md)。parent 负责用户对话与记录，planner/researcher 只读调查并返回设计草稿与依据。

来源：Superpowers 6.3.0 `skills/brainstorming/SKILL.md` 及规格审查模板。适配：按实际不确定性分流、集中澄清、沿用授权；不运行上游视觉服务器，不自动提交规格。

## 选择深度

| 任务 | 处理 |
| --- | --- |
| 讨论、提问、方案评估 | 核查材料后给判断；没有执行或落盘授权时不改文件、不建记录、不把建议转成实现 |
| 可行性研究 | 定义待验证问题、最小探查、证据标准与预算；结果是有来源的建议，原型是否纳入交付依实际授权 |
| 已有流程中的明确小改动 | 读当前实现与验收，说明相关技术取舍后直接做已授权工作，无需另写规格或再批准 |
| 新系统或改变模块关系 | 核对现有结构、关键约束及下游影响，形成可独立验证的规格与计划 |

用户说“能帮我实现”属于工作请求，不能仅因“能”字归为只做研究。已授权执行中的状态问题先回答再继续，不当作取消任务。发现复杂性增加时先判断是否改变授权范围；范围内调整技术方案并记录，新增业务决定才由父会话集中处理。

## 工作步骤

1. 读项目事实：最新目标、不可变条件、结果用途、验收、用户决定、已有文档、相关文件与当前改动。列出已知约束、可查证疑点和真正待决问题；指定来源与口径不能自行替换。独立子系统先按输出与接口划分，例子只按用户表达的格式或深度使用，不自动缩减整体范围。
2. 父会话一次整理影响目标、范围、业务口径、成本及验收的问题，每项给 2-3 个可行选项、推荐和取舍。对已确认或材料可查的事项直接使用结论；只读角色将问题包交父会话，不向用户另起对话。
3. 对实质方案比较 2-3 条路径，结合既有实现、依赖、风险和可撤回性推荐最简单可行方案。不要添加与当前目标无关的重构。
4. 写清相关边界、数据流、接口、错误行为和验证方式；简单任务几行即可，无需完整长规格。已授权执行或要求保存讨论时，父会话在 `.ctbz-record` 保存规格及用户决定；纯评估直接返回判断。既有批准在未被新要求更改时继续有效。
5. 用 [规格/计划审查模板](../templates/document-review.md) 自查适用的缺件、矛盾、歧义和范围；独立审查由风险决定。已授权实现且规格满足目标可进入 [规划](writing-plans.md)，小改动可直接执行；只要求评估时交付评估，到此结束。

验收：待建行为和成功标准可被另一角色一致理解，关键决定有来源，未决事项不会被推荐冒充确认。研究结论允许不可行或证据不足；不把文字方案当作功能完成。
