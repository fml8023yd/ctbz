# Ponytail：最简可行实现

先读 [共享契约](contract.md)。适用于 parent、planner、implementer、debugger、tester、reviewer 的代码设计、实现与评审；只读角色返回建议，不修改文件。

来源：CTBZ `skills/ponytail/SKILL.md`，与 DietrichGebert/ponytail 的固定对照来源关联，详细修订与许可见随包来源记录。适配：保持 YAGNI 与最小有效检查，不缩减明确需求，不限制用户请求的说明。

先读任务和实际调用链，再按顺序选择第一个能完整满足验收的做法：已有能力是否已覆盖；仓库现有 helper/模式；标准库；原生平台；已安装依赖；最后才新增最少实现。选择应能解释边界和副作用，不为追求一行把错误隐藏。

1. 找到问题真正归属与所有相关调用者。修复共享根因，不能只补用户提到的那个症状路径；范围超出 write-set 时回父会话调整。
2. 实现请求的完整可用结果，复用已有结构。没有当前用途的抽象、配置、框架与“以后会用”脚手架不添加；需要时才拆文件，避免无关重构。
3. 输入信任边界、数据保护、错误处理、可访问性和用户明确需求不能省略。标准库两个方案同样简单时选边界正确的那个；物理设备需要真实校准参数时保留。
4. 让验证与风险相称：分支、循环、解析、安全/资金路径有能发现实际错误的运行检查；简单机械编辑用对应核验，不为每个函数搭框架。复用 [TDD 方法](superpowers/test-driven-development.md) 与 [测试参考](references/writing-good-tests.md)。
5. 只有选择了有已知上限的简化，才在合适位置用 `ponytail:` 说明上限及升级条件；不要为所有正常简单实现添加注释。报告说明实际做了什么、验证和必要限制。

用户明确指定 lite 时完成需求并简述更简方案；full 默认复用/标准库优先；ultra 可更积极删除多余代码，但不能删掉用户要求的能力。模式仅在当前任务或用户明确启用的范围内生效；“stop ponytail”或“normal mode”停止风格偏好，不取消质量要求。

验收：最小改动仍覆盖全部需求，测试证明真实行为，新增依赖与抽象都有当前用途。简洁不等于少读代码或少交付。
