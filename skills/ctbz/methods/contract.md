# CTBZ 方法执行契约

本文件是所有内置方法与派发模板的共同前提。先读取父会话提供的任务契约，再读取本契约及被选中的方法。方法不会增加角色工具、写集合或用户授权。

## 目标、阶段与来源

普通任务与循环任务都先提炼目标、不可变条件、结果用途和完成标准，核对用户最新要求及仍有效的既有决定。单纯讨论、提问或评估只调查并给判断，不据此实施改动、初始化记录或发布；“帮我实现/修好/交付”按工作请求推进。正在执行时的提问先回答再续作，只有明确暂停、取消或不兼容的新目标才改变原工作。

简单任务直接执行；复杂任务先用几行说明理解，计划深度随影响范围、不可逆性和判断难度调整。自主完成当前目标必需的依赖、修复和检查；非必需功能、重构、平台化及治理改造只列建议，不执行或阻塞交付。用户的例子通常说明格式或深度，不自动限定全部范围；简化表达不能缩减必要事项或验收。

先核查现有代码、技能、数据入口和权威产物的适用性。用户指定的来源、样本粒度、时间口径、标签、模型版本和交付形式作为输入约束，不静默替换。查不到时说明已查入口、范围及缺口，未经核查不能扩大为整个系统不存在。原要求无法满足时如实保留未完成项；替代分析或检查须明确标为替代，并说明不能证明哪些原要求。

批量处理、数据和语义判断按 [验证参考](references/writing-good-tests.md) 落实关键约束：先检查正例、反例与不确定情形，再扩展执行；样例与必要全量检查分别记录覆盖范围。可确定、可重复的检查优先脚本化，预期结果独立于待测实现；不以声明“已遵守”代替版本、字段、关联键、时间边界或输出值的实际核验。

## 调度与授权

父会话是唯一调度者、对用户的澄清入口和项目状态记录写入者。设计阶段①—⑦优先委派可独立验收的事实调查、草稿、原型、测试和任务细化；主会话保留关键裁决、审定与必要复核，不因其模型能力强就包办机械工作。文档内容生产可委派给已有写权限的执行角色，须指定路径、write-set、依据和验收；只读角色仍只返回草稿。未审定稿与权威版本明确区分，确认和生效状态仅由父会话记录。子 Agent 不派生 Agent，不自行选择或升级模型，不另起执行会话。主会话直接完成普通小任务、未初始化任务或用户禁止子 Agent 的任务；使用方法不要求先建立团队。

父会话先查已确认目标、口径、授权及现有材料。已授权小修复可以直接理解、实现、验证，不重复索要设计批准。可由证据解决的疑点先调查；授权内的技术细节由负责模块决定并说明依据。只有新增或改变目标、业务口径、费用、外部操作、权限、验收及不可逆操作等真正未决事项回到父会话，父会话集中列出影响和 2-3 个选项。相互依赖的关键问题一次整理，不逐题打断。等待必要答案时保留现场，推进无依赖的已授权工作。

每次真实派发或模型重选都由父会话使用本安装的 `initialize select`，服从已加载 profile、调用规则、并发和失败预算。委派对象仅来自草台班子已配置、已激活且宿主已加载的团队；父会话决定角色，团队选择规则决定具体 profile 与模型，不另组临时团队、不硬编码模型、不用通用 Agent 替代团队角色。未初始化、未激活或无合法候选时报告派发阻塞，只继续原协议允许的主会话工作。方法不指定便宜、最强或高一档模型。没有更高档合法模型时可补资料、把模块拆小、由父会话处理或如实阻塞，不能缩减用户验收或绕过配置，不通过切模型克服权限拒绝。新增计费范围没有既有授权时，先准备可审查的依据，再由父会话处理授权。

多 Agent 用于可独立验收的分工或有明确对象的复核；审查强度与风险相称。评审提供具体反例、证据或覆盖缺口，不以人数、轮数或模型强弱证明质量。“规格与质量”是两个检查维度，不要求两名审查者。按当前验收完成必要检查且无阻塞问题后停止扩展，保留可延期建议。

## 角色与工具

以本安装 [角色清单](../角色清单.json) 为准。planner、reviewer、explorer、researcher、reporter 只读返回草稿或证据，不写计划、报告、评审包或项目 JSON，不运行 shell。缺少输入时向父会话报告精确文件与用途；不借用 Git 命令、全局同名技能或另一安装补齐。researcher 仅在其已有权限内检索公开资料，不外发业务数据。

implementer、debugger、tester 仅在指定 worktree 和 write-set 内改动、运行已授权验证；不修改项目主记录。除任务契约明确由父会话传达的提交授权与分工外，Git 提交及集成由父会话处理。父会话可直接修复授权内的小问题，修后同样提供证据并更新受影响评审材料。

索引 `tools` 表示消费方法所需的最小工具，不是授予权限。混合角色方法中的执行步骤只由父会话或已有对应工具与写权限的角色执行；只读角色消费所提供证据并报告缺口。

## 单套项目记录

项目执行记录、原始报告、修复轮次和验证证据位于 `.ctbz-record`。设计稿、ADR、计划及交接材料按用户选择的设计目录保存，先咨询、无指定默认 `./docs/design/`；项目记录引用其绝对路径和版本，不复制第二份权威稿。此目录约定也适用于 brainstorming/writing-plans 等方法的设计产物，其他运行记录位置不变。项目状态由父会话落盘，文档可由授权执行角色在指定写集合内生产、由父会话审定，并用以下身份关联：

| 身份 | 填写方式 |
| --- | --- |
| project | 项目绝对路径及 dashboard 中的实际项目 ID |
| node | 已存在的 task/experiment 节点 ID；group 只汇总 |
| run/task | 有团队 manifest 时用实际 run ID、task ID 和 manifest 路径 |
| parent-only | 无团队 manifest 时 run 明确填 `parent-only`，task 使用项目内稳定 ID，不伪造 agentId 或初始化记录 |

建议材料路径为 `.ctbz-record/methods/<node>/<run>/<task>/`，内含 `brief.md`、`report-<round>.md`、`review-<round>/` 等。ID 作为单路径段；使用已有实际 ID，不从标题推断身份。父会话将绝对材料路径传给角色。目录命名是证据组织约定，不创建第二套状态机。

执行 manifest 是团队任务执行状态的依据；dashboard 是项目目标、决定、轮次、控制和知识的依据；Markdown 是原始证据或可读投影，勾选框和报告中的 DONE 不独立完成任务。父会话核实真实回执与非空证据后，通过现有 `team-state`/`dashboard` 接口更新状态。方法不直接编辑 JSON 绕过校验。AI 经验保持 experience，只有已获明确授权的知识才升级 confirmed。

## 恢复与停止

新会话先读已有 dashboard、项目记录与相应 manifest，核对当前目标、已确认决定、权威产物、作废版本和剩余缺口，再核对同一 node/run/task 的回执、worktree 状态和评审摘要。历史摘要、旧自动任务和代理转发不得覆盖用户更新后的目标。manifest 已接受 completed 而看板投影失败时，先修投影，不重新派发；若新证据推翻旧结果，按修订流程保留旧证据并纠正。旧 run 接管保留原 session、原因与未决工作，不自动恢复真实旧 Agent。安装或配置漂移按初始化错误处理。

收到用户或评审纠偏时先核实事实，不先附和、认错或重跑全部流程。记录“失效假设 → 受影响产物/版本 → 作废结论 → 修正与重验范围”，保留仍有效的证据；事实未明确时写待核实。使用既有计划修订、成果版本、知识替代和 revise-task 留痕，不另建状态系统。连续尝试没有新增证据时换诊断路径，不堆叠同类重试。

暂停、停止、重试预算耗尽、没有可执行依赖或缺少必要授权时保存检查点。控制请求由父会话实际执行后确认。完成一次 run 不等于完成项目，网页状态不证明真实 Agent 存活。恢复只从最后经证实的检查点继续。

同一目录的独立任务分别登记 scope 所有者和 epoch。新建或接管 run 后先用 team-state checkpoint 核对旧执行、请求和计划，再派发。绑定执行事实由 manifest 维护；用户的修订或重开请求通过 revise-task 留存旧证据后处理，再按 requestId 回执。具体参数与状态规则见 [工作范围、回执与成果](../references/dashboard-workflow.md)。

## 验收与保留

代码任务验证行为，研究任务验证假设和证据。负结果若满足预定实验与证据要求，可以用 `outcome=rejected` 完成；未执行、断流或缺证据不能算完成。每次报告记录 result、evidence、method、pitfalls、outcome 和后续方向，不能为了循环凭空扩张目标。

完成声明区分文件已生成、程序已运行、来源已核实、结果已验证和用户目标已达到，不能由前一项推断后一项；对应当前版本、实际执行和原定验收。交付简述结果、关键证据、未验证项与缺口；用符合结果使用者要求的形式交付，内部审查和过程材料按归档要求保存，不默认塞入主交付包。

收尾长期保留规格、决策、原始评审、修复原因、内容摘要、测试日志、接管历史和经验。worktree 清理服从 [现有所有权契约](../references/worktrees.md)，不因任务完成删除过程资料。Git 提交、push、发布及清理沿用实际授权，不由方法自动触发。

## 内置资源边界

运行入口是 [索引](index.json) 中的 16 个普通 Markdown 文件，必要材料由 `resources` 列明。原始上游及脚本是惰性归档的 source-only 材料，不是运行依赖；初始化与方法读取不解包或执行它们。无需 Graphviz、上游视觉服务器、全局辅助技能、hooks 或联网 npm 安装。需要展示结构时先用文本或表格；需用户项目自己的工具时按任务实际环境与授权处理。
