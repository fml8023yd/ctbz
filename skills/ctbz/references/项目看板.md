# 项目看板与阶段记录

运行条件：Node.js 22+；无安装依赖、无构建步骤、无数据库。前端图布局与图标已本地打包。普通任务和循环任务共用同一个看板，真实工作由 ZCode 父会话执行。

1.5.0 的独立任务、会话所有权、检查点、请求回执、成果表及迁移协议见 [工作范围、回执与成果](dashboard-workflow.md)。本页保留基础概念与入口。

## 启动

已授权执行任务需要项目记录，或用户明确要求建立看板/保存讨论时使用以下入口。纯讨论、提问和评估不自动 init、serve 或改记录；可以只读已有材料。任务进行中的提问不自动取消原有执行。

```sh
node <skill>/scripts/dashboard init --workspace <项目绝对路径> --title <项目名> --goal <目标> --mode normal
node <skill>/scripts/dashboard serve --workspace <项目绝对路径> --port 18921
```

循环任务将 mode 设为 loop。serve 可重复传入 --workspace，在同一网页切换已登记项目。默认只监听 127.0.0.1，端口占用时选其他端口。不要随意覆盖、清空已存在的项目记录。

项目状态在 `.ctbz-record/dashboard.json`，每次变更同时生成人类可读的 `.ctbz-record/记录.md`；登记成果在 `.ctbz-record/artifacts/`。JSON 为结构化状态依据；配置含锁和 revision，界面遇并发冲突应先重新载入，再确认修改。任务记录不包含凭据、完整模型原始配置或应用数据库。

## 主进程读写

```sh
node <skill>/scripts/dashboard show --workspace <项目绝对路径>
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action node.upsert --file <节点变更JSON绝对路径>
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action heartbeat --file <空对象JSON绝对路径>
```

登记独立 work 组（顶层 group 节点，自带独立 scope）：先 `work.create` 建组，再 `scope.claim` 认领归属；更新既有组用 `work.upsert`，重复 create 会被拒（WORK_EXISTS）：

```sh
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action work.create --session <当前会话> --file <组定义JSON绝对路径>
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action scope.claim --session <当前会话> --file <认领JSON绝对路径>
```

```json
{"node": {"id": "ud1-compact", "title": "UD1紧凑化"}, "work": {"goal": "紧凑化与状态透出", "mode": "normal"}}
```

```json
{"scopeId": "ud1-compact", "sessionId": "<当前会话>"}
```

action 名只接受 store 内合法集合，写错会返回完整清单（UNKNOWN_ACTION）。

payload 必须是 JSON 文件。用结构化 API 写文件，不把用户文字拼成 shell 命令。示例节点变更：

```json
{
  "node": {
    "id": "feature-window",
    "parentId": null,
    "kind": "experiment",
    "title": "比较不同统计窗口",
    "status": "planned",
    "owner": "researcher",
    "score": 75,
    "scoreReason": "可直接验证当前最关键的不确定性",
    "dependsOn": []
  }
}
```

未绑定执行批次的主会话任务，开始工作改 status=active。完成时 status=completed，并填写 result、evidence 数组、method、pitfalls、nextSteps；outcome 是 supported、rejected 或 inconclusive。证据不足时明确记录，不填虚构性能数字。执行错误或依赖缺失用 blocked 并说明原因。绑定 run 的任务只能通过 team-state 同步执行事实，网页重开或修订使用请求协议。

树上 group 是汇总，task 与 experiment 是可执行工作。依赖在 dependsOn 指向已有节点；拒绝父子循环和依赖循环。优先级 share 只在可执行候选间归一化，不是项目进度。完成度按任务数量计算，新增范围会改变分母；研究树不能用进度百分比声称科学目标已达成。

## 决策与知识

question.upsert 的 question 包含 id、title、context、2-3 个 options（id、label、reason）和 recommendedOptionId。question.resolve 记录用户实际选择的 optionId 或自由文本 answer。推荐项不能直接当作答案。

knowledge.upsert 的 entry 包含 id、title、content、sourceNodeIds、source、scope、confidence。新条目默认 experience。只有用户实际确认后才能 knowledge.confirm；网页按钮形成 user 事件。CLI 的 --actor user 仅用于记录用户已经明确做出的决定，不能由 AI 自行提升权限或伪造确认。需要把条目作废时，由用户明确决定后调用 knowledge.reject 保留历史。新版本用 supersedesId 关联旧 confirmed 知识，用户确认替代后旧版变为 superseded，保留历史。未解决的问题可编辑或作废，已解决的问题保留真实答案。

## 循环闭环

```sh
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action round.start --file <空对象JSON绝对路径>
node <skill>/scripts/dashboard apply --workspace <项目绝对路径> --action round.finish --file <轮次总结JSON绝对路径>
```

round.start 默认选最高分可执行候选，也可以传 nodeId。固定保存当时排序，记录第 N 轮；上一轮未结束时不能再开下一轮。可以设置 maxRounds 和时间预算；时间预算由主进程在检查点判断，轮次上限由脚本检查。总结包含 summary、method、pitfalls、conclusion 和 nextSteps，必须反映已完成的实际验证。

每轮只推进一个方向，方向内部允许子任务并行。节点出现交叉依赖时使用 dependsOn，不要重复创建同一工作。完成当前问题后可以新增更细的问题，不应自动把整个研究方向标为彻底完成。

1.4.0 允许对已经包含子模块的方向显式 `round.start`，payload 为 `{"nodeId":"direction"}`。该方向至少有一个就绪后代且自身/祖先未阻塞、依赖已满足；方向可用 group。候选优先级仍只分配给可执行叶节点，父方向不重复计权。默认自动选择仍选最高分叶节点；父会话需要一轮内并行兄弟模块时，显式选共同方向。完成 group 前所有后代需完成或取消；有后续待研究子节点时用检查点 blocked 结束本轮并保留待办。

每个检查点读取所在 scope 的 requests 和计划变更。control.request 仅建立请求；父会话核实在途工作，用绑定 requestId 的 control.ack 分别记录 received、completed 或 failed。仅 pending 可撤回或明确替代；暂停/停止请求会阻止新派发，完成回执要求范围内无在途执行。团队任务用 team-state checkpoint 对账和采用实际读过的计划。heartbeat 只记报到，不能替代检查点。网页不能直接创建 Agent，服务也不能调用任意 shell。

## 任务记录衔接

team-state init-run/update-task 在接受原 manifest 后同步项目看板，保留用户编辑的计划字段。原 manifest 是执行事实依据，看板维护项目目标、决策、轮次与知识；Markdown 是可读记录。同步失败返回显式 warning，不能宣称同步成功或重新派发已接受的任务。每个 run 的读改写及投影在同一锁下串行执行，worktree 记录写入使用同一锁；进程被强制停止留下 .json.lock 时先确认原 PID 已退出，再手工移除，不自动抢锁。

派发契约及 task JSON 使用稳定 taskId、nodeId 和 parentId。nodeId 显式绑定看板已规划的 task/experiment；parentId 与现有树一致，group 不接 Agent 执行。没有 nodeId 的旧任务继续使用 runId/taskId 生成的稳定 ID；带 parentId 的新任务投影到指定父分支。一个节点只能属于同一 run/task，已有绑定不可换；循环中运行节点必须在当前方向内。升级后的新 run 不复用已有执行绑定节点，应增加后续节点并保留来源。

完成任务要求 verification/review/integration 的状态和非空白证据。completed/cancelled 任务的普通 update-task 仅接受相同重试；用户请求修订或重开时，主会话使用 revise-task 保留旧任务快照后执行，再通过检查点完成回执。不要在网页直接改已绑定执行任务的终态来绕过 manifest。终态 run 使用 sync-run 补完整投影；显式重开会保留 run 的历史收尾记录。

```sh
node <skill>/scripts/team-state finish-run --state-dir <select返回目录> --team ctbz --session <当前会话> --run-id <任务ID> --summary <真实总结> --status completed
node <skill>/scripts/team-state sync-run --state-dir <原run所在目录> --team ctbz --session <当前会话> --run-id <任务ID>
node <skill>/scripts/team-state adopt-run --state-dir <原run所在目录> --team ctbz --session <当前已激活会话> --run-id <任务ID> --reason <接管原因>
```

completed 要求任务全部完成或取消且无在途执行；blocked、cancelled 同样保留现场。结束 run 不自动结束整个项目。父会话最终确认全部目标验收后才更新项目 phase=complete 和 status=completed。

相同 finish-run 可幂等重试，先补全部任务投影再记收尾，重复调用不增加相同事件。新会话在同一配置 generation 内 activate 后，显式 adopt-run 保留原 session、原因和接管时间；这只转交记录所有权，不恢复真实旧 Agent。跨 generation、跨机器或配置漂移不自动迁移。接管后主进程核查旧在途任务，依据真实回执继续、标阻塞或按失败协议处理。

## 汇报与导出

```sh
node <skill>/scripts/dashboard export --workspace <项目绝对路径> --format markdown --audience leader
node <skill>/scripts/dashboard export --workspace <项目绝对路径> --format markdown --audience owner
```

领导版围绕目标、结果、风险和待决事项；本人版保留任务、轮次与知识表。数据源相同，不隐藏失败。导出只生成材料，不自动发送给别人。JSON 导出用于归档，恢复前应检查目录和版本，不能盲目覆盖现有记录。

## 远程查看

在需要 FRP 时，为远程查看单独启动 --read-only 实例，并用 --token-env CTBZ_DASHBOARD_TOKEN 从环境读取访问令牌。不要在 URL、文档、命令行参数或日志里写令牌。非 loopback 监听必须开启令牌。

frpc 可将本机只读端口映射到已有阿里云 frps；端口、安全组、TLS 和访问方式按服务器实际配置处理。公网应使用 HTTPS，不通过裸 HTTP 传令牌或项目内容。技能不包含服务器地址、账户或密钥，安装到新用户电脑时不能继承原作者服务器权限。

浏览器与主进程状态分开显示：最近同步、最近实际检查点、待确认控制请求。主会话退出、机器休眠或隧道断开时保留最后记录，并明确未知或过期状态，不伪称研究仍在运行。
