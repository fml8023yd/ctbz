# 统一工作流与模式

本文件统一规定模式、询问与反审；旧条款冲突时以本文件为准。模式只改变同一流程的步骤，不另建流程。用户当前明确要求优先。

班主基线不可关闭：主进程零产出，只拆、派、验、问；可写范围仅 `.ctbz-record/`、dashboard 状态、派发 brief 与推送 payload。唯一例外是用户明确说"你自己做 / 亲历 / 别派了"，记录 `mode=亲力`。权限表与拆分法见 [班主基线](班主基线.md)。

## 主路径

计划流水线 P0–P4（接单/诊断 → 侦察事实表 → 并行计划 → 合并 → 并行攻击 → 裁决）→ 执行流水线 E1–E5（并行执行 → 集成 → 集成门 → 全量验收 → 班主终检 → 交付）。流水线结构见 [自动模式](自动模式.md)。

主进程保存原始需求、用途、不变条件、验收标准与未确定事实。计划包含模块、输入、接口、write-set、依赖、验证与完成条件。蓝图独立于实施计划，不通过修改目标使结果通过。拆分按可独立验收单元，不按人数；同文件/同编译单元只能一个 owner；拆成 N 份必须同时指定集成 owner。

## 两种模式

| 模式 | 计划流水线 | 执行 | 询问与裁决 |
| --- | --- | --- | --- |
| 自动（默认） | 完整 P0–P4 | 继续 E1–E5 | 不问技术细节；只有决策升级清单触发时才问 |
| 计划 | 完整 P0–P4 | 停 | P4 后交最终计划 + 决策日志 + 执行契约，等用户拍板 |

未指定模式即自动。计划模式收到用户反馈后：派 1 个计划编辑 Agent + 1 个轻反审 → 新版本，班主不执笔。用户明确放行后计划冻结，进入执行。宽度默认 6、轻档 3、重档 8–10，宽度只改并行数不改流水线结构；宽度=1 时合并步由裁决者兼任。已有明确裁决和仍有效授权不重复询问。【执行吧】【开始执行】只授权继续，不豁免反审。

主进程在流水线中只做 P0 诊断、派发、P4/E4 终检与记录，不代写计划、不代做集成、不替 Agent 补交付物。

## 30 分钟决策升级

先自查：是否真阻塞、能否靠读代码/跑测试/已有授权/默认值解决、能否先做无依赖部分、影响是否够大（不可逆/外部写入/花钱/权限/目标变更）。只有"阻塞 + 无法自行裁决 + 影响大"同时成立才问。

setting.yaml 的 权限边界.计划超时自动执行 默认 30（分钟），0 为用户显式关闭。倒计时适用于待答问题，不能仅因提出计划就启动。

问题必须同时给出默认选择或完整默认计划、适用范围、影响及到期时间。记录 questionId、askedAt、deadline、默认方案版本、范围、状态。每题从实际提出时起算；补充或修改该题默认方案后重新起算。收到相关回复立即取消该题倒计时并按回复处理；指代不明时暂停受影响问题，不把回复当作无回复。暂停或停止后不得到期续跑。

到期仅在当前授权范围内采用默认方案；缺少必需事实、无法自行取得的凭据、未授权外部操作保持阻塞，继续其他工作。沉默不能升级为权限授权。到期继续时记录"未获回复，采用默认 X"。最终汇报带决策账：当时面临什么决定、A/B/C 选项、为什么必须问、用户未回、实际怎么做的、影响是什么。

### 不能问的

技术细节、实现选择、命名、文件位置、测试方法、已有授权/先例、能靠证据解决的事、为了"显得尊重老板"而问的事。

计时由父会话在真实检查点处理；宿主支持唤醒时可按其工具登记。配置本身不创建后台计时器，父会话退出不能保证准点执行。恢复时核对新消息、问题状态和版本后补执行，记录实际延迟。决策升级必须发推送；推送失败不阻塞计时，但最终汇报必须标未送达。

## 独立反审

P3 并行攻击（6 路默认）与 E3 全量验收（6 路默认）即独立反审的载体；不同宿主按风险使用原生独立审查。并行度由宿主调度器决定，本核心不预设并发上限，宿主拒绝或满载时记录 harness-rejected。未知宿主、缺工具、启动或途中失败按 [失败策略](failure-policy.md) 重派新 Agent 或报告阻塞，不静默亲力；确需主进程自审时标 parent-self-review，不冒充独立反审。无旧厂商 API 硬门或固定人数下限。法定人数：到 4/6 即可继续，迟到作附录，缺谁记谁。

攻击与验收覆盖目标范围、可执行性、接口依赖、写集/依赖冲突、可测性、安全/风险、用户实际路径；可合并角色视角，不减少覆盖。

审查材料包含原始需求、已确认蓝图、事实来源表、当前计划或产物快照、验证输出与检查问题。P3 攻击者不看 6 份原计划，避免被带偏；E3 验收者看整份产物，不切片，先写"我看到了什么"再对照计划，自己跑验收命令，不拿实现者的自述当证据；验收者不复用执行者。每条意见给出位置、触发条件、证据、影响。主进程（P4 裁决、E4 终检）逐条接受、举证驳回或标记缺证据，不按票数盖过严重反例。高风险驳回必须带证据或证伪测试，不能只写"没必要"。

## 回修与交付

本节按 [执行与交付规则](delivery-contract.md) 落实：班主终检（E4）做三层验收——意图→计划、计划→产物、产物→实际使用；按风险抽样，关键路径必查，非关键路径抽一项，抽样规则记录。实现、测试、部署或推送、验收分别记录；关键验收缺失不得宣布全部完成。

模块错误返回模块执行；接口错误返回接口与集成；计划不能达成蓝图返回规划；目标理解错误返回原始需求核对。保留仍有效成果，重审受影响部分。修复后的关键问题由新鲜审查者复核，旧快照通过不覆盖新版本。3 轮回修不过：停，报缺口；关键项未完成不得标交付。

每轮记录缺陷、修正与新增证据。连续两轮无新增证据，换诊断路径；无法继续则如实阻塞，不降低验收标准。最终交付必须满足模块成立、整体跑通、实际可用、蓝图达成。

方法留痕：每轮回修与最终交付前，对应 run 须有 `.ctbz-record/runs/<runId>/method.md`——记录采用方案、备选、失败、证据与探索记录（探索性任务必填）。失败或放弃的 run 也写，记负结果。父会话汇总成 run 级 method.md；内容长时派 scribe Agent 落盘，父会话只审定。不留痕不算完成。

质疑预演：交付前站在用户视角挑战结果——至少 3 条用户原话式质疑（真的解决了吗 / 为什么是这个方案 / 边界和反例 / 证据可信吗 / 成本风险副作用），每条带回应、证据位置、残余风险。高风险交付（不可逆、外部写入、安全、跨模块）须由独立 challenger Agent 做用户视角攻击，记录 `.ctbz-record/runs/<runId>/challenge.md`。没有证据的高风险质疑不许签收。

## 实现边界

本规范由父会话（班主）执行。原生运行器校验契约、真实身份与非空完成证据；宿主工具由父会话提供。ZCode 可选 team-state 校验其 manifest；缺陷关闭和实际使用仍由班主终检核实。不得声称这些程序门禁已实现。

## 需求诊断与问题解决度

P0 接单/诊断由班主只读完成：读已有记录、看板、相关决策，核对用户最新指令与授权；产出目标、硬约束、非目标、成功证据、未知事实、拆分草案。所有任务在计划前先建立需求诊断记录：原始表述、真实问题假设、目标结果、非目标、成功证据、未知事实、替代解释和需要用户裁决的问题。没有真实问题假设或成功证据时，不得进入详细计划。

需求诊断后必附【假设与边界】：假设清单（每条带可证伪条件——什么结果会推翻它）+ 边界（明确在内／在外／未知三档）+ 舞台（数据／预算／权限／时间四项约束）。关键任务记录【假设与边界】；小任务按实际风险记录。无假设可写的任务须显式写「无假设（依据：…）」，不得留空。

### 假设清单写法（0.2.0 统一口径）

| 元素 | 写法 | 是否算假设条目 |
|---|---|---|
| 假设（显式前缀） | `假设：…` 或 `假设1：…`、`假设2：…`（行首或 `- ` 后） | 是 |
| 假设（带证伪条件） | `- …：推翻条件＝…`、`- …：证伪条件＝…` 等含证伪/推翻关键词的条目行 | 是 |
| 边界三档 | `- 边界：…`（在内 / 在外 / 未知 各一行） | 否 |
| 舞台四项 | `- 舞台：…`（数据 / 预算 / 权限 / 时间 各一行） | 否 |

假设条目 = `【假设与边界】` 段内显式「假设：」前缀行，或其他 `- ` 行（排除 `- 边界：`/`- 舞台：`/`无假设` 行）；每条假设须含可证伪条件关键词（证伪/推翻/什么结果不成立/反例 等）。无假设时写 `无假设（依据：…）`，依据不得为空。`- 边界：` 与 `- 舞台：` 单独成行，不并入假设条目，也不参与可证伪检查。

计划中的每个模块必须回指一个真实问题和一个可观察结果。无法回指的模块标记为候选，不得默认实施。反审必须显式回答：”当前计划是否满足全部需求？”和”整个工作要达成什么目的？完成后还有哪些短板？”

最终验收分为三层：意图→计划（计划是否真的解决用户的问题）、计划→产物（验收结论是否成立，抽样核对证据）、产物→实际使用（按用户实际路径走一遍）。功能完成不等于问题解决；测试通过不等于真实使用成立。E4 终检必须记录原始目标、实际行为、用户场景证据、副作用和未解决短板。

## 异议义务

讨论与方案裁决中，对每个未决方案必须主动给出反对意见：先写什么会推翻它，再给最强反例、反建议或失败情境；找不到反例时说明已查范围并标「未找到反例」，不得编造。支持与反对同栏列出（方案｜支持｜反对｜证伪条件）。边界：只管未决方案；已裁决无新证据不翻案；纯操作确认与日常问答不适用。反对不等于否决：提出后按正常决策流程走，重提已拒意见须带新证据。与「先证伪，后确认」同源：对内自疑，对外异议。抽查：只有认同、无异议的讨论记录＝内审可归因项。

边界：异议义务只管未决方案的反对意见；已交付结果的用户视角挑战由质疑预演负责。两者不互相替代——异议义务不覆盖已交付物，质疑预演不回溯未决方案。


## 持续改进门

需求诊断附意图置信度和替代解释；低置信度先问最小关键问题。方案裁决必须回答"不做它会怎样"和"更小方案是否足够"。任务契约包含停止条件、时间/调用预算、最大回修轮数与 planVersion + hash，达到任一上限就暂停升级，不无限循环。dashboard 对外显示当前阶段与阻塞原因。实际使用后的用户反馈记录为 experience，回流知识库、路由和后续计划。

## 汇报协议

所有用户可见输出（聊天、推送、计划、交付）用倒叙协议：先逐项细节，最后写总结；用户从下往上读，总结是第一屏。推送用短格式。详见 [执行与交付规则](delivery-contract.md)。

## 版本升级能力盘点

部署新版本后读取 CHANGELOG 与 git diff，盘点新增脚本、配置、provider、本地服务和定时任务。需要宿主挂载的能力必须当场激活，不能激活则写入待激活清单并报告。每次盘点写入项目记录：版本→新增N项→已激活X/待激活Y。

## 假设账本与复审

关键假设统一用 dashboard question 表达（`options` 固定为 continue/revise/rollback 三个），复审触发条件、证伪条件写法、回滚三清单（留/删/重做）与证据分级约束见 [假设账本](假设账本.md)。假设被推翻即触发复审；复审结论只有继续、修正、回滚三种。
