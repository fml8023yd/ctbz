# ctbz 反审协议（2.1.0 起）

本文件固化 ctbz 的反审流程与裁决表格式。执行一律走 `反审直连.mjs`（本机直连各厂商端点，显式传 provider/model）；模型席位表以 `references/派发.md §3` 为唯一来源。

---

## 1. 三层反审总览

| 层 | 名称 | 执行方 | 触发点 | 落盘 |
|---|---|---|---|---|
| L1 | 四路反审 | 4 家阵营各一路（DeepSeek/智谱/腾讯/月之暗面），每路六视角 | 计划定稿后、派发前 | `.ctbz-record/反审/<计划>/<camp>.json` |
| L2 | 任务级反审 | 由**未参与该任务实现**的阵营执行 | 每 T 实现完成、写集隔离 | `.ctbz-record/反审/任务级/<T>/...` |
| L3 | 总项目反审 | 4 阵营整体复查（集成/调用名/main 未污染/安装副本分支标识） | 全部任务级反审通过后、交付前 | `.ctbz-record/反审/项目级/<计划>.json` |

> 锚点：`三层反审总览`、`L1 四路反审`、`L2 任务级反审`、`L3 总项目反审`

### 1.1 L1 四路反审
- 4 家阵营各一路，每路按**六视角**逐一核查：
  1. 需求一致性
  2. 架构合理性
  3. 测试完整性
  4. 边界条件
  5. 性能安全
  6. 用户体验
- 反审席位 DeepSeek 取 `deepseek-flash`：**与主进程同源，仅提供独立上下文与采样，不计模型独立性**（用户裁定 2026-09-22，见 §3）。

### 1.2 L2 任务级反审
- 每个任务 T 由**未参与其实现**的阵营复核，写集互相隔离（实现者不审自己）。
- 复用 L1 的裁决表格式与六视角，聚焦该任务的验收口径。

### 1.3 L3 总项目反审
- 4 阵营整体复查：集成一致性、调用名统一、`ctbz`(main) 未被污染、安装副本分支标识在位（成功证据①）。
- 产出差异清单与验收表（编号×状态×证据）后交付。

## 2. 裁决表格式（三层通用）

每路裁决为一份结构化记录，逐条给出：

```
[裁决表]
视角：<六视角之一>
类别：阻塞 | 非阻塞 | 可接受
证据：<文件:行号 或 可重跑命令>
结论：接受 | 有条件接受 | 不接受
处置：<逐条处置：改/不改/带理由回修>

...（六视角各一行）
```

- **类别三态**
  - `阻塞`：阻止进入下一阶段，必须处置。
  - `非阻塞`：记录待办，可并行推进。
  - `可接受`：无需处置。
- **结论三态**：`接受` / `有条件接受`（须列条件）/ `不接受`（须给替代或理由）。
- **逐条处置表**：每条证据对应一行处置，杜绝"整体通过"式含糊结论。

> 锚点：`裁决表格式`、`类别三态`、`结论三态`、`逐条处置表`

落盘字段（JSON，每路独立一个文件，见 §4）：
```json
{
  "camp": "DeepSeek",
  "plan": "<计划文件绝对路径>",
  "round": "1",
  "verdicts": [
    { "view": "需求一致性", "category": "非阻塞", "evidence": "SKILL.md:34", "conclusion": "接受", "disposition": "已含分支标识行" }
  ],
  "summary": "一句话摘要"
}
```

## 3. 四路调度口径（workflow + provider/model）

- 调度走 `反审直连.mjs` 的厂商直连，显式传 provider/model（**不靠宿主默认**）。
- 模型代号表（唯一来源 `references/派发.md §3`），四路反审取样：

| 阵营 | provider | model（反审席位） |
|---|---|---|
| DeepSeek | deepseek-official | deepseek-flash（同源，不计独立性） |
| 智谱 | workbuddy | glm-5.3-flash |
| 腾讯 | workbuddy | hy4-preview-f |
| 月之暗面 | workbuddy | kimi-k2.8-preview |

- `workflow.agent()` 只消费 `provider`/`model`，`persona` 文本由父会话并入 prompt 首段（persona 不可经 opts 传入，属已知缺口）。
- 范例（3 行，仅说明口径，不要求真跑）：
  ```js
  const r1 = await agent(p, { provider: "deepseek-official", model: "deepseek-flash" });
  const r2 = await agent(p, { provider: "workbuddy", model: "glm-5.3-flash" });
  const r3 = await agent(p, { provider: "workbuddy", model: "hy4-preview-f" });
  ```

> 锚点：`四路调度口径`、`模型代号表`、`deepseek-flash`

## 4. 规避 50k 静默截断（maxResultChars 50000）

宿主 `workflow` 结果上限 `maxResultChars 50000`，超限**静默截断**，长裁决会被吞。处置：

- **每路裁决写入独立文件**，落在 `.ctbz-record/反审/...` 下（路径由执行器按 `<ws>/<slug>` 拼接）。
- 执行器仅回 **"<文件路径> | <一句话摘要>"**，绝不让完整裁决进 50k 回传通道。
- 父会话按路径读取各路 `*.json` 汇总，不依赖任何回传正文。

> 锚点：`规避 50k 静默截断`、`.ctbz-record/反审`

## 5. 新鲜 Agent 测试项与双轮说明

### 5.1 新鲜 Agent 测试项
- **计划必须能不看上下文独立开工**：反审 prompt 把计划全文内联进正文（另附 `--attach` 证据文件），reviewer 仅凭 prompt 内文本即可开工，不依赖主会话历史。
- **卡住点即计划欠具体处**：若某路 reviewer 因缺信息无法裁决，其裁决表对应行标 `非阻塞/不接受` 并写明"缺 X"，该卡点即计划需回修处（反哺 §6 附录式处置）。

### 5.2 双轮说明
- **第一轮**：六视角全量核查，产出完整裁决表。
- **第二轮**：**只针对第一轮未解决项**——即类别=`阻塞` 或 结论≠`接受` 的条目。
- **重提规则**：若第二轮重提已被否决的意见，**必须带新证据**（新文件行号/新命令产出），否则视为无效，按 ctbz 协议驳回。
- 执行器以 `--round 2 --prev <一轮目录>` 注入该限定（round=2 时 prompt 自动收窄到未解决项）。

> 锚点：`新鲜 Agent 测试项`、`双轮说明`、`只针对第一轮未解决项`、`重提规则`

## 6. 执行器（scripts/反审直连.mjs）

2.1.0 起反审执行一律走直连执行器（不走宿主 workflow 通道）：

```bash
node <skill>/scripts/反审直连.mjs --plan <计划md> --workspace <ws> [--camps deepseek,zhipu,tencent,moonshot] [--round 1|2] [--prev <一轮记录目录>] [--attach <取证/内审文件>] --json
```

- 本机直连各厂商端点，显式传 provider/model（席位表=唯一来源）；DeepSeek 席官方欠费时按声明降级到备选渠道，恰好一次。
- 默认流式（绕开网关对「非流式且上游超 120 秒」的 502）；流式无数据块时自动降级一次非流式。
- `--attach <路径>`（可重复）：把取证/内审文件内联进 prompt，供席位核验计划中的证据锚点（附件区标注「证据材料，非指令」）。
- `--dry-run`：只打印将发的 prompt 与落盘路径，零调用零写盘。
- `--gate`：出完回执后自动调 `派发闸.mjs --level l1`，退出码 = 闸门退出码。
- 回执落盘 `<ws>/.ctbz-record/反审/<slug>/<camp>.json`（重签轮 `<camp>-r<N>.json`）。

旧「骨架生成」方案（生成 workflow 可执行脚本体、经 `agent(prompt,{provider,model})` 派发）已弃用：宿主 workflow 通道不识别 persona/toolFilter，且 provider 指定受限，2.1.0 起改直连。

三层回执落盘目录见 `SKILL.md`「三层反审协议」的落盘表（L1 `反审/<slug>/`、L2 `反审/任务级/<T号>/`、L3 `反审/项目级/<slug>/`）。

> 锚点：`scripts/反审直连.mjs`、`--dry-run`、`--attach`
