# ctbz 反审协议（dsh 版）

本文件固化 ctbz 在 dsh 宿主上的反审流程与裁决表格式。调度一律走 dsh 的 `workflow` 工具，显式传 `provider`/`model`；不依赖 ZCode 注册链。模型代号表以 `references/派发.md §3` 为唯一来源。

---

## 1. 三层反审总览

| 层 | 名称 | 执行方 | 触发点 | 落盘 |
|---|---|---|---|---|
| L1 | 四路反审 | 4 家阵营各一路（DeepSeek/智谱/腾讯/月之暗面），每路六视角 | 计划定稿后、派发前 | `.ctbz-record/反审/<计划>/<camp>.json` |
| L2 | 任务级反审 | 由**未参与该任务实现**的阵营执行 | 每 T 实现完成、写集隔离 | `.ctbz-record/反审/任务级/<T>/...` |
| L3 | 总项目反审 | 4 阵营整体复查（集成/调用名/main 未污染/安装副本分支标识） | 全部任务级反审通过后、交付前 | `.ctbz-record/反审/项目级/<计划>.json` |

> 锚点：`三层反审总览`、`L1 四路反审`、`L2 任务级反审`、`L3 总项目反审`

### 1.1 L1 四路反审
- 4 家阵营各一路，每路按**六视角**逐一核查：
  1. 需求一致性
  2. 架构合理性
  3. 测试完整性
  4. 边界条件
  5. 性能安全
  6. 用户体验
- 反审席位 DeepSeek 一律取 `deepseek-v4-pro`（避开主进程 `deepseek-flash` 同模型自审，见 §3）。

### 1.2 L2 任务级反审
- 每个任务 T 由**未参与其实现**的阵营复核，写集互相隔离（实现者不审自己）。
- 复用 L1 的裁决表格式与六视角，聚焦该任务的验收口径。

### 1.3 L3 总项目反审
- 4 阵营整体复查：集成一致性、调用名统一、`ctbz`(main) 未被污染、安装副本分支标识在位（成功证据①）。
- 产出差异清单与验收表（编号×状态×证据）后交付。

## 2. 裁决表格式（三层通用）

每路裁决为一份结构化记录，逐条给出：

```
[裁决表]
视角：<六视角之一>
类别：阻塞 | 非阻塞 | 可接受
证据：<文件:行号 或 可重跑命令>
结论：接受 | 有条件接受 | 不接受
处置：<逐条处置：改/不改/带理由回修>

...（六视角各一行）
```

- **类别三态**
  - `阻塞`：阻止进入下一阶段，必须处置。
  - `非阻塞`：记录待办，可并行推进。
  - `可接受`：无需处置。
- **结论三态**：`接受` / `有条件接受`（须列条件）/ `不接受`（须给替代或理由）。
- **逐条处置表**：每条证据对应一行处置，杜绝"整体通过"式含糊结论。

> 锚点：`裁决表格式`、`类别三态`、`结论三态`、`逐条处置表`

落盘字段（JSON，每路独立一个文件，见 §4）：
```json
{
  "camp": "DeepSeek",
  "plan": "docs/ctbz-dsh-实施计划-20260921.md",
  "round": "1",
  "verdicts": [
    { "view": "需求一致性", "category": "非阻塞", "evidence": "SKILL.md:34", "conclusion": "接受", "disposition": "已含分支标识行" }
  ],
  "summary": "一句话摘要"
}
```

## 3. 四路调度口径（workflow + provider/model）

- 调度走 dsh `workflow` 的 `agent(prompt, opts)`，显式传 `opts.provider` / `opts.model`（**不靠 harness 默认**）。
- 模型代号表（唯一来源 `references/派发.md §3`），四路反审取样：

| 阵营 | provider | model（反审席位） |
|---|---|---|
| DeepSeek | deepseek-official | **deepseek-v4-pro** |
| 智谱 | workbuddy | glm-5.3-flash |
| 腾讯 | workbuddy | hy4-preview-f |
| 月之暗面 | workbuddy | kimi-k2.8-preview |

- `workflow.agent()` 只消费 `provider`/`model`，`persona` 文本由父会话并入 prompt 首段（persona 不可经 opts 传入，属已知缺口）。
- 范例（3 行，仅说明口径，不要求真跑）：
  ```js
  const r1 = await agent(p, { provider: "deepseek-official", model: "deepseek-v4-pro" });
  const r2 = await agent(p, { provider: "workbuddy", model: "glm-5.3-flash" });
  const r3 = await agent(p, { provider: "workbuddy", model: "hy4-preview-f" });
  ```

> 锚点：`四路调度口径`、`模型代号表`、`deepseek-v4-pro`

## 4. 规避 50k 静默截断（maxResultChars 50000）

`workflow` 结果上限 `maxResultChars 50000`，超限**静默截断**，长裁决会被吞。处置：

- **每路裁决写入独立文件**，落在 `.ctbz-record/反审/...` 下（路径由骨架自动拼接 `RECORD_DIR`）。
- `workflow` 仅回 **"<文件路径> | <一句话摘要>"**，绝不让完整裁决进 50k 回传通道。
- 父会话按路径读取各路 `*.json` 汇总，不依赖 workflow 回传正文。

> 锚点：`规避 50k 静默截断`、`.ctbz-record/反审`

## 5. 新鲜 Agent 测试项与双轮说明

### 5.1 新鲜 Agent 测试项
- **计划必须能不看上下文独立开工**：骨架把计划文件路径**原样烤进**常量 `PLAN`，reviewer 仅凭该路径与自身视角即可开工，不依赖主会话历史。
- **卡住点即计划欠具体处**：若某路 reviewer 因缺信息无法裁决，其裁决表对应行标 `非阻塞/不接受` 并写明"缺 X"，该卡点即计划需回修处（反哺 §6 附录式处置）。

### 5.2 双轮说明
- **第一轮**：六视角全量核查，产出完整裁决表。
- **第二轮**：**只针对第一轮未解决项**——即类别=`阻塞` 或 结论≠`接受` 的条目。
- **重提规则**：若第二轮重提已被否决的意见，**必须带新证据**（新文件行号/新命令产出），否则视为无效，按 ctbz 协议驳回。
- 骨架通过 `ROUND` 与 `PREV_DIR` 注入该限定（round=2 时 prompt 自动收窄到未解决项）。

> 锚点：`新鲜 Agent 测试项`、`双轮说明`、`只针对第一轮未解决项`、`重提规则`

## 6. 骨架生成（scripts/反审.mjs）

生成可直接交 `workflow` 执行的 JS 脚本体：

```bash
/usr/local/bin/node <skill>/scripts/反审.mjs --plan <计划md> [--camps deepseek,zhipu,tencent,moonshot] [--round 1|2] [--prev <一轮记录目录>] --dry-run
```

- `--dry-run`：打印骨架到 stdout 并用 `new Function` 校验语法（workflow 沙箱无 Node API，骨架不引用任何 fs/network）。
- 生成的骨架含 `PLAN`/`SIX_VIEWS`/`CAMPS`/`ROUND`/`PREV_DIR`/`RECORD_DIR` 常量，循环四路 `agent(prompt,{provider,model})`，每路落地独立 `*.json` 并仅回路径+摘要。
- 骨架体可被 JS 解析（见自验 a）。
- `--workspace <ws>`：回执根目录，**非 `--dry-run` 时必填**（缺则 exit 2）；骨架的 `RECORD_DIR` 为 `<ws>/.ctbz-record/反审/<slug>` 绝对路径。
- `--gate`：骨架产出后自动调 `派发闸.mjs --level l1`，退出码 = 闸门退出码；闸门 stdout 接本进程 stderr，不污染骨架 stdout。

三层回执落盘目录见 `SKILL.md`「三层反审协议」的落盘表（L1 `反审/<slug>/`、L2 `反审/任务级/<T号>/`、L3 `反审/项目级/<slug>/`）。

> 锚点：`scripts/反审.mjs`、`--dry-run`、`可被 JS 解析`
