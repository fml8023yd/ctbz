# 假设账本与复审（操作规范）

读者：实施 Agent。目的：让「这个方法现在这么做到底对不对」变成有触发、有落点、有结论的机制，而不是靠谁想起来才问。

## 1. 什么进账本

门槛：**这条假设若被推翻，会导致已有产物作废或方向改变**。技术细节、实现选择、命名、临时参数不进。
每个关键任务在需求诊断的【假设与边界】里出现的假设，凡满足此门槛的，同步登记为 dashboard question。

## 2. 固定写法（一律映射到 dashboard question）

假设统一用 `question.upsert` 登记，不新建数据类型：

| 语义 | 字段 |
| --- | --- |
| 假设陈述 | `title`（一句话，可被独立判断真假） |
| 证伪条件 | `context`（必须可执行或可复算：写明数据源、算式、复算时点） |
| 处置选项 | `options`，**恰好 3 个，id 固定** `continue` / `revise` / `rollback` |
| 推荐项 | `recommendedOptionId` + 每个 option 的 `reason`（含证据来源） |

`scopeId` 按项目 scope 结构填；无独立 scope 填 `null`。

### 证伪条件：合格与不合格

- ✅ 合格：「若 T+7 日我方成本估算 ÷ 上游账单实扣 < 0.95 或 > 1.05，则成本口径假设被推翻；数据源 /api/log/self，每日 09:00 复算。」
- ❌ 不合格：「如果效果不好」——不可判定。
- ❌ 不合格：「毛利率 ≥ 35%」——阈值来源不明，未绑定数据源与采集时间。

## 3. 复审触发条件（任一满足即复审，不复审不算完成）

1. **阶段退出时**：退出判据核对前，对账本内所有 open 假设各复审一次。
2. **连续 3 轮无新增证据**：3 轮 round 没有产生能改变任一假设判断的新证据，主动复审存疑假设。
3. **成本/口径不一致**：任一面板值与实测值偏离超过该假设证伪条件允许的带宽（例：面板 46% vs 实测 27%）。
4. **用户新信息与已记录假设相矛盾**：必须是**可逐条对账的矛盾**——用户话里的事实断言与账本某条的 context/证伪线一一对应冲突，才触发；「用户说了句新话」不构成触发。触发时列出：假设 id、矛盾点、证据出处。
5. **关键指标跌破证伪线**：任一假设的证伪条件被复算击穿，立即复审，不等阶段退出。

## 4. 复审输出只有三种

| 结论 | 动作 |
| --- | --- |
| **继续** | `question.resolve {optionId: "continue"}`；不改任何产物。 |
| **修正** | `question.resolve {optionId: "revise"}`；在 answer 里列受影响产物清单与重验范围。 |
| **回滚** | `question.resolve {optionId: "rollback"}`；在 answer 里**必须列三张清单：留哪些、删哪些、重做哪些**。回滚语义沿用 [流程治理.md](流程治理.md)「违规与补救」：不追认则按用户指示回滚；回滚由父会话派独立复核，原干活方不给自己签验收。 |

注意：
- `resolve` 是决定语义。**只有用户（或经用户授权的父会话按授权记录）才能 resolve**；Agent 自身复审只登记 question、更新 context 证据，不冒充用户裁决。Agent 记录的结论须标来源（如「E1 实施者复审，依据 XXX 复算」）。
- 复审结论不用 `round.finish` 记（它只对 `mode=loop` 生效）。
- 证伪条件没有专属字段，全部写在 `context` 里；复审发现证据后更新 context 并留下 history（`question.upsert` 自动记）。

## 5. 与证据分级的关系（写死，不例外）

复审结论若基于推测而非实测（本包常用分级：【验】=有账本/代码实证、【半】=存在但本次未复跑、【未】=理论推断），**必须标 `assumed`，且不得作为回滚依据**。回滚只认【验】级证据或用户裁决。`assumed` 结论只允许触发「再取一次证」或维持现状，不得据此删产物。

## 6. 反面清单

- 不把「再看看」「后续观察」当复审结论——三种之外的输出不存在。
- 不给已被实测推翻的假设推荐 `continue`。
- 不因为「假设是我的工作前提」就跳过登记——前提越硬越要登记。
