# 原生派发契约 0.1.0

## 路由

1. 从当前工具列表填写 `source=current-harness-tool-list`、`harness=codex|zcode`、真实 `tools` 精确名。目录存在、模型名、旧 profile 均不能证明宿主能力。
2. 读取对应私有 adapter 与唯一全局核心。父 Harness 或用户配置 wrapper 注入原生端口；没有 shell 生成工具或默认 API 执行器。
3. 父会话核对写集合与依赖无冲突；并行度由宿主调度器决定，本核心不预设并发上限，也不能用空任务清单放行越权派发。宿主拒绝或满载时记录 harness-rejected 与真实回执。独立任务和 worktree 必须无写冲突。
4. Codex 调 `collaboration.spawn_agent`：task_name 小写/数字/下划线，模型 plan/discuss=gpt-6-astra，其余=gpt-6.1-sol，显式模型 fork_turns=none。父会话通过消息和终态取得真实结果；wait_agent 仅等待通知。
5. ZCode 使用本次已加载原生工具或合法 profile；toolNames 与工具映射由当前 wrapper 提供。可选 profile select 失败按 [失败策略](failure-policy.md) 报告阻塞，不调用旧厂商 API 补位。

## 任务身份

每个派发 brief 必须声明任务身份：任务在流水线中的位置（P0.5/P1/P2/P3/P4/E1/E2/E3 等）与在该任务中的身份（explorer / planner / merger / attacker / adjudicator / implementer / integrator / acceptor / scribe / challenger）。challenger 用 reviewer 权限，不新增 profile 角色；其余同上。同一 Agent 一次只承担一个任务身份。回执按任务身份归档，验收者不复用执行者。

## 独立任务数据

```json
{
  "taskId": "module_one",
  "role": "implementer",
  "taskIdentity": "E1.implementer",
  "phase": "implement",
  "planVersion": "plan-<hash>",
  "workspace": "/absolute/project",
  "objective": "Concrete requested result",
  "context": "User intent, chosen design/version, constraints and upstream/downstream interfaces",
  "authorization": "Human authorization and permitted scope",
  "inputs": ["/absolute/project/docs/design/design.md"],
  "writeSet": ["/absolute/project/src/module.js"],
  "acceptance": ["Observable result and verification command"],
  "stopConditions": ["Permission denied; user pause; budget exhausted"],
  "budget": {"maxRepairRounds": 3},
  "methods": ["verification-before-completion"]
}
```

核心验证角色、阶段、任务身份、绝对路径、只读角色空 writeSet、验收、授权、停止条件和回修预算，并注入共享 contract 与实际方法绝对路径。任务 message 必须独立完整；fork_turns=none 不继承对话。角色工具与 writeSet 是指令契约，原生宿主未强制隔离时不宣称有 sandbox。

## 流水线派发点

| 阶段 | 派什么 | 输入 | 产出 |
| --- | --- | --- | --- |
| P0.5 侦察 | 1–2 个 explorer（只读） | 班主 P0 诊断草案 | 事实表：相关文件路径、接口、数据流、依赖、约束、未知项、风险 |
| P1 并行计划 | 6 个计划 Agent（默认；轻档 3、重档 8–10），不同镜头，互不可见 | 同一 brief + 同一事实表 | 各自计划：目标复述、方案、任务拆分、writeSet、依赖、集成 owner、验收命令、风险、替代方案、未知项 |
| P2 合并 | 1 个合并 Agent | 6 份原计划 | 合并稿 + 分歧清单 + 每模块采用谁、为什么、丢了什么 |
| P3 并行攻击 | 6 个攻击 Agent，不同镜头，互不可见，不看 6 份原计划 | 原始需求 + 事实表 + 合并稿 + 分歧清单 | 每条攻击带触发条件、证据、影响、建议或证伪测试；允许"没发现实质缺陷" |
| P4 裁决 | 1 个裁决 Agent | 6 份原计划 + 合并稿 + 分歧清单 + 6 份攻击 + 原始需求 | 最终计划 + 执行契约 + 决策日志 |
| E1 并行执行 | M 个执行 Agent，按写集并行，冲突串行 | 绑定 planVersion + hash 的任务 brief | 回执：改动文件、行为说明、验证输出、未完成项、风险、基线差异 |
| E2 集成 | 1 个集成 Agent（集成 owner 唯一，不是班主） | E1 回执与产物 | 合并接口、构建/组合测试结果 |
| E3 全量验收 | 6 个验收 Agent，不同镜头（含用户质疑），各看整份产物，不复用执行者 | 通过集成门的产物 | verdict + evidence + issues + 未覆盖项 + 用户质疑清单 |

任务简单、事实已足够时 P0.5 可跳过，班主记录理由。宽度只改 P1/P3/E3 的并行数，不改流水线结构；宽度=1 时合并步由裁决者兼任。

## 版本绑定与跨 run 写集锁

- 裁决产出执行契约时生成 `planVersion + hash`；每个 E1 任务 brief 绑定该版本，回执声明实际使用的 planVersion。
- 计划修订产生新 planVersion；旧版本产物不冒充新版本验收。
- 跨 run 写集锁：同一 run 内写冲突任务排队；跨 run 写同一文件的任务也排队，不冲突才并行。冲突判定以 brief 声明的 writeSet 为准。

## 法定人数

P1/P3/E3 默认 6 路，到 4/6 即可继续：迟到结论作附录补记，缺谁记谁（agentId 与原因），不因个别 Agent 失联重跑整组。

## 回执与接管

回执：实际 agentId、taskId、sessionId、status、result、evidence、checkpoint、planVersion、method。method 含做了什么、备选、失败、证据，只读角色返回方法观察。完成必须证据非空；没有真实身份不编造。代码运行器中的 port.start/wait/stop 由父 Harness 提供；wait 需返回真实 Agent 终态，stop 返回 true 需确认已停。同步宿主（一次调用即返回终态回执）可把 wait 映射为恒等；端口不再要求在途计数，并行度由宿主调度器决定。

未知宿主、缺 adapter/工具、启动/途中失败按 [失败策略](failure-policy.md) 处理：重派新 Agent、报告阻塞、或经用户明确授权后亲力；不静默接管执行。途中断流先确认旧子进程停下，再核查检查点和已有文件；不能确认则状态 awaiting-stop，先处理停旧执行。权限拒绝停止被拒动作，不触发绕过。

项目状态由父会话通过 dashboard 写入；ZCode 可选 team-state 只在使用其 profile manifest 时使用。日志记录真实状态，模拟测试端口不冒充真实集成。
