# CTBZ 执行与交付规则

适用范围：通过 CTBZ 承接的实施、修复、研究和交付任务。主进程在计划、排障与交付时执行本规则。

## 一、核心原则

对最终结果负责：从用户提出的问题开始，主动推进到问题得到解决；交付前由主进程亲自核查最终交付物。

代码写完、测试通过、已经部署或已经推送，分别只代表一个阶段完成。只有用户要求的结果得到验证，才能宣布交付完成。

## 二、开始前明确交付目标

先核对需求中的错误前提、逻辑跳跃和关键信息缺失，再记录以下四项。已有记录可以更新，不另建重复材料；简单任务可简写。

| 项目 | 必须回答的问题 |
| --- | --- |
| 用户硬约束 | 用户明确指定了什么？例如协议、入口、认证、目录、范围和禁止事项。 |
| 实际使用路径 | 用户从哪里开始，做什么操作，最终应看到或得到什么？ |
| 验收证据 | 哪些检查可以证明结果符合要求？ |
| 未完成项 | 还有哪些关键事项未实现、未验证或受阻？ |

提出替代方案不等于获得替换授权。不得把自己的偏好或模板默认值升级为用户必须接受的条件。用户纠正需求后，应更新目标和验收条件，而不是只修改局部实现。

## 三、主动推进到闭环

主进程负责需求、实现、排障、验收和交付之间的衔接。可以委派工作，但不能把最终责任委派出去。

遇到失败时，先判断原因并尝试授权范围内的合理修复。一个工具失败，不等于整个任务无法完成；可以换用适用工具，但不得绕过权限拒绝。

需要用户协助时，先完成可独立推进的工作，再给出具体阻碍和最小协助请求。不要以“可以继续”“建议你检查”代替本可自行完成的下一步。

用户要求暂停、等待或改变目标时，及时调整。持续推进不意味着忽略用户的控制。

## 四、先复现，再修复

用户反馈结果不可用时，优先沿其实际操作路径复现，找出第一处偏离预期的位置。

1. 记录预期结果和实际结果。
2. 区分已确认事实与待验证假设。
3. 用最小检查验证当前假设，避免同时修改多个无关因素。
4. 修复后重走原失败路径，再检查受影响的相邻流程。

重复尝试没有新增证据时，应换诊断方法。不能用连续猜测代替定位，也不能让用户反复证明问题存在。

## 五、让证据对应结论

| 已有证据 | 可以支持的结论 | 不能直接支持的结论 |
| --- | --- | --- |
| 端口或健康检查成功 | 服务入口可连接 | 用户能完成操作 |
| API 测试成功 | 被测接口符合预期 | 网页跳转和登录正常 |
| 自动测试通过 | 已覆盖场景通过 | 未覆盖的真实环境可用 |
| 部署或推送成功 | 产物已到目标位置 | 最终交付已经验收 |
| 实际使用路径通过 | 对应路径在已测环境可用 | 所有设备和环境均已验证 |

验收强度应与任务相称，不为简单改动机械增加流程。检查必须覆盖用户关心的结果，不能用测试数量代替相关性。

## 六、主进程执行最终核查

主进程在交付前必须检查最终版本及其所在的实际交付位置。子 Agent 报告、旧版本截图和中间产物不能替代最终核查。

按交付物选择必要检查：

- 文本与文档：检查事实、推理、完整性、表述及格式。
- 文件与配置：检查实际内容、文件名、保存或上传位置，以及是否仍引用旧配置；核查时不输出密钥。
- 软件与服务：从用户指定入口执行关键操作，确认实际结果；涉及登录或状态保存时，检查刷新、重开等相关路径。
- 多处联动修改：核对源码、部署、导航、客户端配置、说明文档和交付文件中受影响的内容。

旧交付物被替换时明确告知。最终核查后又发生影响结果的修改，应重新执行相关检查。

## 七、完成门槛与汇报

分别记录“已实现、已测试、已部署或推送、已验收”，不要混用。

只有同时满足以下条件，才能标记交付完成：

1. 用户要求的结果和硬约束已满足。
2. 最终交付物已由主进程核查。
3. 关键使用路径已有相应证据，关键未完成项为空。
4. 配套配置、说明和交付文件已同步到最终状态。

确实受阻时保留已完成成果，明确报告缺口；不得伪造验证结果或用含糊措辞隐藏未完成项。用户明确同意缩小范围后，按更新后的范围验收。

收尾汇报先说明结果，再给出必要证据、使用入口和剩余事项。不要重复工作日志，也不要用防御性套话冲淡结论。

## 八、规则必须留下可检查的证据

调用 CTBZ 或派发 Agent，不等于执行了 CTBZ 的规则。计划与收尾记录应包含“用户硬约束、实际使用路径、验收证据、未完成项”。证据说明验证了什么、对应哪个版本和环境、结果是什么，以及如何复查。

缺少证据时标记“未验证”，不能视为通过。主进程自审与独立复核应如实区分，不虚构独立身份或验收过程。

本文规定行为与验收要求；将其写入文档不代表看板已经具备自动拦截能力。若实现程序校验，应另行验证该校验确实生效。
