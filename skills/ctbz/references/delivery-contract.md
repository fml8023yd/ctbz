# CTBZ 执行与交付规则

适用范围：通过 CTBZ 承接的实施、修复、研究和交付任务。班主（主进程）在计划、排障与交付时执行本规则。

## 一、核心原则

对最终结果负责：从用户提出的问题开始，主动推进到问题得到解决；交付前由班主亲自核查最终交付物。班主基线不可关闭：班主零产出，只拆、派、验、问，可写范围仅 `.ctbz-record/`、dashboard 状态、派发 brief 与推送 payload（见 [班主基线](班主基线.md)）。

代码写完、测试通过、已经部署或已经推送，分别只代表一个阶段完成。只有用户要求的结果得到验证，才能宣布交付完成。最终责任不因派发而转移：可以委派工作，不能把最终责任委派出去。

## 二、开始前明确交付目标

先核对需求中的错误前提、逻辑跳跃和关键信息缺失，再记录以下四项。已有记录可以更新，不另建重复材料；简单任务可简写。

| 项目 | 必须回答的问题 |
| --- | --- |
| 用户硬约束 | 用户明确指定了什么？例如协议、入口、认证、目录、范围和禁止事项。 |
| 实际使用路径 | 用户从哪里开始，做什么操作，最终应看到或得到什么？ |
| 验收证据 | 哪些检查可以证明结果符合要求？ |
| 未完成项 | 还有哪些关键事项未实现、未验证或受阻？ |

提出替代方案不等于获得替换授权。不得把自己的偏好或模板默认值升级为用户必须接受的条件。用户纠正需求后，应更新目标和验收条件，而不是只修改局部实现。

## 三、主动推进到闭环

班主负责需求、派发、验收和交付之间的衔接；实现、集成、评审由 Agent 流水线完成。遇到失败时按 [失败策略](failure-policy.md) 处理：重派新 Agent、报告阻塞、或经用户明确授权后亲力；不静默接管执行。一个工具失败，不等于整个任务无法完成；不得绕过权限拒绝。

需要用户协助时，先完成可独立推进的工作，再给出具体阻碍和最小协助请求。不要以"可以继续""建议你检查"代替本可自行完成的下一步。

用户要求暂停、等待或改变目标时，及时调整。持续推进不意味着忽略用户的控制。

## 四、先复现，再修复

用户反馈结果不可用时，优先沿其实际操作路径复现，找出第一处偏离预期的位置。

1. 记录预期结果和实际结果。
2. 区分已确认事实与待验证假设。
3. 用最小检查验证当前假设，避免同时修改多个无关因素。
4. 修复后重走原失败路径，再检查受影响的相邻流程。

重复尝试没有新增证据时，应换诊断方法。不能用连续猜测代替定位，也不能让用户反复证明问题存在。

## 五、让证据对应结论

| 已有证据 | 可以支持的结论 | 不能直接支持的结论 |
| --- | --- | --- |
| 端口或健康检查成功 | 服务入口可连接 | 用户能完成操作 |
| API 测试成功 | 被测接口符合预期 | 网页跳转和登录正常 |
| 自动测试通过 | 已覆盖场景通过 | 未覆盖的真实环境可用 |
| 部署或推送成功 | 产物已到目标位置 | 最终交付已经验收 |
| 实际使用路径通过 | 对应路径在已测环境可用 | 所有设备和环境均已验证 |

验收强度应与任务相称，不为简单改动机械增加流程。检查必须覆盖用户关心的结果，不能用测试数量代替相关性。

## 六、班主终检与三层验收

E4 班主终检按三层验收执行，逐层记录：

| 层 | 问题 | 做法 |
| --- | --- | --- |
| 意图 → 计划 | 计划是否真的解决用户的问题 | 对照 P0 诊断记录与原始需求 |
| 计划 → 产物 | 验收员的结论是否成立 | 抽样核对证据，不拿验收摘要当事实 |
| 产物 → 实际使用 | 用户路径是否走得通 | 按用户实际路径走一遍 |

按风险抽样：关键路径必查，非关键路径抽一项；抽样规则记录。子 Agent 报告、旧版本截图和中间产物不能替代终检。

按交付物选择必要检查：

- 文本与文档：检查事实、推理、完整性、表述及格式。
- 文件与配置：检查实际内容、文件名、保存或上传位置，以及是否仍引用旧配置；核查时不输出密钥。
- 软件与服务：从用户指定入口执行关键操作，确认实际结果；涉及登录或状态保存时，检查刷新、重开等相关路径。
- 多处联动修改：核对源码、部署、导航、客户端配置、说明文档和交付文件中受影响的内容。

旧交付物被替换时明确告知。最终核查后又发生影响结果的修改，应重新执行相关检查。

## 七、完成门槛与汇报

分别记录“已实现、已测试、已部署或推送、已验收”，不要混用。

只有同时满足以下条件，才能标记交付完成：

1. 用户要求的结果和硬约束已满足。
2. 最终交付物已由班主三层验收核查。
3. 关键使用路径已有相应证据，关键未完成项为空。
4. 配套配置、说明和交付文件已同步到最终状态。

确实受阻时保留已完成成果，明确报告缺口；不得伪造验证结果或用含糊措辞隐藏未完成项。用户明确同意缩小范围后，按更新后的范围验收。

## 汇报与推送

倒叙汇报协议：所有用户可见输出先逐项细节（做了什么、关键证据路径/命令/版本、问题/风险），最后写总结（现状、已完成、未解决/风险、决策账、下一步）。用户从下往上读，总结是第一屏，必须能独立回答"现在什么情况、还差什么、下一步做什么"。

推送：ServerChan，内容为结果、证据位置、缺口、下一件；不带密钥。推送失败不阻塞交付，但汇报里标"未送达"。推送短格式：一句话问题 + 选项 A/B/C（每个一行）+ 推荐 + 默认 + 截止时间 + runId。

决策账：凡触发 30 分钟决策升级且未获回复按默认继续的，最终汇报必须列出——当时面临什么决定、A/B/C、为什么必须问、用户未回、实际怎么做的、影响是什么。

收尾问下一件；保留当前 run 记录，追问能直接接上。

收尾汇报按倒叙协议给出结果、证据、使用入口和剩余事项；总结在最后。不要重复工作日志，也不要用防御性套话冲淡结论。

## 八、规则必须留下可检查的证据

调用 CTBZ 或派发 Agent，不等于执行了 CTBZ 的规则。计划与收尾记录应包含“用户硬约束、实际使用路径、验收证据、未完成项”。证据说明验证了什么、对应哪个版本和环境、结果是什么，以及如何复查。

缺少证据时标记"未验证"，不能视为通过。班主自审（parent-self-review）与独立复核应如实区分，不虚构独立身份或验收过程。

本文规定行为与验收要求；将其写入文档不代表看板已经具备自动拦截能力。若实现程序校验，应另行验证该校验确实生效。

## 九、交付门槛：方法留痕 + 质疑预演（0.2.0）

除第七节完成门槛外，交付完成前还须满足下面两条留痕门槛。不留痕、不预演不算交付完成。

### 9.1 方法留痕门槛

每个 run 交付前，`.ctbz-record/runs/<runId>/method.md` 必须存在。

| 要求 | 说明 |
| --- | --- |
| run 级 method.md | 每个 run 结束前写；失败或放弃的 run 也写，记录负结果 |
| 探索记录 | `exploration=true` 的任务须写完整探索记录（假设/探针/观察/结论） |
| 模板字段 | 任务、路径、岔路、证据、可复用方法、探索记录、知识沉淀 |

探索性任务判据（满足任一即 `exploration=true`）：开始时无已知解决路径；第一版方案失败或需换路；需探针/实验/对比定位；结论依赖新证据而非既有知识。

### 9.2 质疑预演门槛

每个 run 交付前，`.ctbz-record/runs/<runId>/challenge.md` 必须存在，至少 3 条用户视角质疑。

| 要求 | 说明 |
| --- | --- |
| 数量 | 至少 3 条，最多 5 条 |
| 每条结构 | 用户原话式质疑 + 回应 + 证据位置 + 残余风险 |
| 证据 | 每条质疑须有证据支撑，或明确标"未验证/缺口" |
| 高风险 | 不可逆、外部写入、安全、跨模块交付，须由独立 challenger Agent 做用户视角攻击 |

没有证据的高风险质疑不许签收：要么补验证，要么标缺口，不得靠话术糊过去。

用户提出的新质疑若不在预演清单，记录并回流下一轮方法留痕。

### 9.3 与现有规则关系

| 关系 | 说明 |
| --- | --- |
| 不替代 E3/E4 验收 | 验收验"计划→产物"；质疑预演练"用户→交付" |
| 不替代异议义务 | 异议义务管未决方案；质疑预演管已交付结果 |
| 不替代独立反审 | 质疑预演可由班主自己做；高风险才加 challenger |

交付汇报须给出两条留痕路径（method.md、challenge.md）。

## 十、交付硬闸：复命清单（0.2.0）

交付前父会话必须跑：

```
node <core>/scripts/内审.mjs 复命 --file <复命清单>
```

`exit≠0` 即不得标交付完成。退出码由脚本给出，不看自述。

### 10.1 复命清单六段格式

段标题行首零缩进恰为 `<段名>:`（或 `<段名>：`），整段仅下列六段，缺任一即判红：

| # | 段名 | 说明 |
|---|---|---|
| 1 | 自主延伸 | 本轮自主做的延伸动作；不得写「无」 |
| 2 | 自主修复 | 本轮自发现并修掉的缺陷；不得写「无」 |
| 3 | 交付前三问 | 答案对齐 / 半途扫描 / 跑偏检查，三行三问各带证据痕迹（2.1.4 起必填） |
| 4 | 待裁决 | 需用户拍板的未决项；不得写「无」 |
| 5 | 自疑 | 自我发现的可疑点 + 证伪实验 + 结果；禁止写「无」 |
| 6 | 行动账增量 | 本轮新增决策账三字段（依据/取舍/证伪），取舍不得为空话；整段可写「无」 |

条目形态：每行以 `- ` 开头；整段恰为「无」时放行（自疑段禁止）。

### 10.2 A / B / C 三类检查

| 类 | 级别 | 触发 | exit 影响 |
|---|---|---|---|
| A | 阻断 | 缺【假设与边界】段；有假设条但缺可证伪条件；豁免「无假设（依据：…）」依据为空；段内零假设条目 | exit≠0 |
| B | 警告 | 结论段出现绝对断言词（证明/确认无误/必然/绝对…）且同段无证据指针 | 不打断 exit |
| C | 阻断 | 回执声明新建脚本，但该路径已在 `~/.ctbz/流程/index.json` 登记，应先复用 | exit≠0 |

A、C 阻断交付；B 只提示，交付前自行补证据指针（`[measured]` / 实测 / 路径:行号 / exit / 数字+来源）。

### 10.3 流程资产缺失降级

`~/.ctbz/流程/index.json` 缺失或损坏时，C 闸不阻断（无法比对），但复命输出必须显式标注「流程资产复用未校验（index.json 缺失）」；班主在交付汇报中同步标「未校验」，不得默认通过。详见 [SKILL.md 流程资产](../SKILL.md)。
