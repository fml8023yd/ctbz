# 自动模式

> 默认自动。计划模式只出计划不执行。班主基线在两种模式下都不可关闭，见 [班主基线](班主基线.md)。

## 一、两种模式

| 模式 | 计划流水线 | 执行 | 何时用 |
|---|---|---|---|
| 自动（默认） | 完整 P0–P4 | 继续 E1–E5 | 用户给任务就走 |
| 计划 | 完整 P0–P4 | 停 | 用户要先看计划 |

- 自动模式不问技术细节；只有“决策升级”清单触发时才问。
- 计划模式在 P4 后交最终计划 + 决策日志 + 执行契约，不执行。
- 计划模式收到反馈：派 1 个计划编辑 Agent + 1 个轻反审 → 新版本。班主不执笔。
- 用户明确放行后，计划冻结，进入执行。
- 决策升级规则见 [班主基线 · 六、30 分钟决策升级](班主基线.md#六30-分钟决策升级)。

## 二、宽度

| 档 | 并行数 |
|---|---|
| 默认 | 6 |
| 轻档 | 3 |
| 重档 | 8–10 |

- 宽度只改并行数，不改流水线结构。
- 宽度 = 1 时，合并步由裁决者兼任。
- 班主记录选择理由。

## 三、计划流水线

| 阶段 | 谁 | 产出 |
|---|---|---|
| P0 接单 / 诊断 | 班主 | 目标、硬约束、非目标、成功证据、未知事实、拆分草案 |
| P0.5 侦察 | 1–2 explorer（只读） | 事实表 |
| P1 并行计划 | 6 计划 Agent | 6 份计划 |
| P2 合并 | 1 合并 Agent | 合并稿、分歧清单、采用理由 |
| P3 并行攻击 | 6 攻击 Agent | 6 份攻击 |
| P4 裁决 | 1 裁决 Agent | 最终计划、执行契约、决策日志 |

### P0 接单 / 诊断

班主读已有记录、看板、相关决策；核对用户最新指令与授权。只读。

产出：目标、硬约束、非目标、成功证据、未知事实、拆分草案。

### P0.5 侦察事实表

1–2 个 explorer 只读产出：相关文件路径、接口、数据流、依赖、约束、未知项、风险。

- 6 路计划必须引用同一份事实表。
- 任务简单、事实已足够时可跳过，班主记录理由。

### P1 并行计划

- 6 个计划 Agent（默认），同一 brief + 事实表，不同角色 / 模型。
- 建议镜头：最小改动、正确性优先、风险优先、用户路径优先、可维护性优先、对抗视角。
- 互不可见。
- 每份计划必含：目标复述、方案、任务拆分、writeSet、依赖、集成 owner、验收命令、风险、替代方案、未知项。

### P2 合并

1 个合并 Agent 读 6 份计划，产出：

1. 合并稿；
2. 分歧清单；
3. 每个模块采用谁的方案、为什么、丢了什么。

不丢少数派；不把 6 份计划揉成模糊共识。

### P3 并行攻击

- 6 个攻击 Agent（默认），镜头：需求覆盖、可行性、写集 / 依赖冲突、可测性、安全 / 风险、更小方案。
- 输入：原始需求 + 事实表 + 合并稿 + 分歧清单。
- 不看 6 份原计划，避免被带偏。
- 每条攻击必须带：触发条件、证据、影响、建议或证伪测试。
- 允许“没发现实质缺陷”。

### P4 裁决

1 个裁决 Agent，输入：6 份原计划 + 合并稿 + 分歧清单 + 6 份攻击 + 原始需求。

产出：

1. 最终计划；
2. 执行契约：任务、writeSet、依赖、集成 owner、验收命令、停止条件、预算、planVersion + hash；
3. 决策日志：采纳 / 驳回 + 理由 + 证据。

高风险驳回必须带证据或证伪测试，不能只写“没必要”。

### 计划模式出口

交最终计划 + 决策日志 + 执行契约。不执行。等用户拍板。

## 四、执行流水线

| 阶段 | 谁 | 产出 |
|---|---|---|
| E1 并行执行 | M 执行 Agent | 各任务产物 + 回执 |
| E2 集成 | 1 集成 Agent | 集成产物 + 构建 / 组合测试 |
| E2.5 集成门 | 班主 / 集成 owner | build + smoke test 结论 |
| E3 全量验收 | 6 验收 Agent | verdict + evidence + issues |
| E4 班主终检 | 班主 | 三层验收结论 |
| E5 交付 | 班主 | 推送、汇报、问下一件 |

### E1 并行执行

- M 个执行 Agent，按写集并行；冲突串行。
- 每个任务 brief 绑定 planVersion + hash。
- 回执：改动文件、行为说明、验证输出、未完成项、风险、基线差异、method（做了什么、备选、失败、证据；只读角色返回方法观察）。
- 任务标 `exploration: true|false`（判据见 [班主基线 · 八、留痕与方法沉淀](班主基线.md#八留痕与方法沉淀)）；探索性任务必须回完整探索记录（假设 / 探针 / 观察 / 结论）。

### E2 集成

- 1 个集成 Agent（不是班主）：合并接口、跑构建 / 组合测试、解决集成问题。
- 集成 owner 唯一。

### E2.5 集成门

- build + smoke test 过了，才允许开 6 路验收。
- 不过打回执行，不浪费验收预算。

### E3 全量验收

- 6 个验收 Agent（默认），镜头：正确性、需求覆盖、安全、性能 / 资源、用户体验 / 实际路径、可维护性。
- 每个验收 Agent 看整份产物，不切片。
- 先写“我看到了什么”：逐文件 / 逐行为说明实际改动、接口、数据流、副作用，带证据位置；再对照计划。
- 自己跑验收命令，不拿实现者的自述当证据。
- 输出 verdict + evidence + issues + 未覆盖项。
- 验收者不复用执行者。

### E4 班主终检

三层验收：

| 层 | 问题 | 做法 |
|---|---|---|
| 意图 → 计划 | 计划是否真的解决用户的问题 | 对照原始需求 |
| 计划 → 产物 | 验收员结论是否成立 | 抽样核对证据 |
| 产物 → 实际使用 | 用户能否真的用 | 按实际路径走一遍 |

按风险抽样：关键路径必查，非关键路径抽一项；抽样规则记录。

质疑预演：交付前按 [班主基线 · 九、质疑预演](班主基线.md#九质疑预演) 走必答清单（至少 3 条、最多 5 条用户视角质疑），每条带证据位置与残余风险；无证据标缺口。高风险交付（不可逆、外部写入、安全、跨模块）加独立 challenger Agent 做用户视角攻击。预演记录 `.ctbz-record/runs/<runId>/challenge.md`。

### E5 交付

- 推送：ServerChan；内容为结果、证据位置、缺口、下一件；不带密钥。
- 推送失败不阻塞交付，但必须在汇报里标“未送达”。
- 交付前方法留痕：汇总 `.ctbz-record/runs/<runId>/method.md`（模板见 [班主基线 · 八、留痕与方法沉淀](班主基线.md#八留痕与方法沉淀)）；失败或放弃的 run 也写，记负结果；不留痕不算完成。
- 交付前质疑预演记录：`.ctbz-record/runs/<runId>/challenge.md` 必须存在。
- 汇报给两条留痕路径（method.md、challenge.md）；汇报用倒叙协议，见 [班主基线 · 七、倒叙汇报协议](班主基线.md#七倒叙汇报协议)。
- 问下一件；保留当前 run 记录，追问能直接接上。

## 五、法定人数与版本

| 项 | 规则 |
|---|---|
| 法定人数 | 6 路到 4 即可继续；迟到作附录；缺谁记谁 |
| planVersion | 计划冻结时分配，执行 brief 全部绑定 |
| hash | 计划正文哈希；产物与版本绑定，改计划升版本 |
| 版本不符 | 拒收回执，不静默采用 |

## 六、跨 run 写集锁

- 同一路径同一时间只有一个 run 持有写锁。
- 新 run 启动先查旧锁；冲突任务排队，不冲突并行。
- 锁记录：路径、runId、owner、epoch、状态。
- 旧 run 失联先确认停止，再释放锁；不静默覆盖。
- 记录 `write-conflict`。
