## 主进程服务姿态（1.6.0 起生效）

1. **多任务并行设计**：用户提出多条低相关性任务时，允许调用多个 Agent 并行进行计划设计（约 50% 程度的并行要求）；工作计划在不影响效果的前提下，尽可能使用多 Agent 并行设计/开发。
2. **快分发、后台跑**：主进程应尽快完成任务分发，使子进程以后台形式（run_in_background）继续工作；子进程结束后主进程再介入进行下一步。
3. **时刻待命**：主进程必须时刻待命接收用户新命令——不得因自己在做计划或开发而让用户等待；长任务一律后台化，主会话保持可响应。
4. **文字经济学**：用户的注意力是最高成本资源，写出的每个字能被读到都是奢望。回复默认极简（结论先行、表格优先、细节折叠为"要看细节说一声"）；反审/实施/验证过程只在聊天留一行状态，全文落盘归档。内部详尽、对外吝啬。**执行自检**：发出前问"删掉一半还成立吗？成立就删"。
5. **反审规模分级**：反审 Agent 数随改动面缩放——单文件小改 2-3 个，模块级 4-6 个，架构级 6+；框架级 ≥3、完整级 ≥4 下限不变。用户未指定时按改动面自动定级并在派发时声明。
6. **write-set 按可编译单元切**：任务契约的 write-set 按能独立编译/验证的单元划分，接口定义与实现同文件时必须同一 write-set，禁止按关注点拆出"编译死锁"（互相等待）。

## 快速模式与自动模式（1.6.0）

**快速模式**：用户说"快速模式"即进入验证优先变体——设计好即干，不管实现脏净，只管当前目标与结论；"快速模式"命令本身即反审豁免（等价【执行吧】+验证优先），不以任何方式缩减反审规模——用户在快速模式内另行命令【反审】时规模照常。产物定性为验证性产出，转正为交付成果须经用户确认或转入正常模式补测试评审。收尾清理仅限本轮自产无保留价值产物（/tmp、临时脚本）；worktree 删除遵循 worktrees.md——dirty/未集成的先列清单经用户逐项确认，禁止批量删除，用户既有文件一律不删。结束前声明"清理了什么/留下了什么"。

**自动模式**：用户说"自动模式"即全自主流水线——设计 → 反审 → 测试 → 开发 → 本地集成验证 → 推送前准备。两条边界：①"自动模式"开启命令即用户对本 run 的一次性反审授权，授权原文与范围记入 run manifest；本授权只覆盖本 run，不构成对"反审由用户命令触发"的全局改写，run 内反审规模按既有规模条款执行。②终点定义为"推送前准备就绪 + 请求授权"——推送依赖用户在场的一次性设备码授权，授权后仅推本 run 声明的仓库与分支（默认 fml8023yd/ctbz main）。红线不因授权失效：删文件、越出声明目录、正式远端变更（A3）照旧拦截。**倒计时触发**（settings 档位 >0 时默认启用）：settings.yaml"计划超时自动执行">0 即倒计时档位全局默认——AI 给出计划后**自动按档位启动限时授权**（到点前 ServerChan 推送提醒、回滚锚点先行、回消息即停），无需每次口令；用户显式说"倒计时执行 N 分钟"可临时覆盖档位；档位=0 时必须显式口令才触发。限时授权语义：授权记录（计划快照、到期时间、执行范围）落盘 .ctbz-record，到期未叫停在下一个可执行机会补执行并明示延迟原因；到期前收到非叫停消息 → 暂停追问一次；宿主 Cron 可作加速器，配额不可用不影响语义。

## 重构模式（1.8.0）

触发：用户点名"重构模式"（【自动重构】= 重构模式 + 自动模式授权，进命令集）；随口"重构一下 X"按普通任务路由，AI 视量级建议升级。十步：

1. **确认重构边界**（范围/非目标/成功标准）
2. **理清逻辑**：产物=【现状行为清单】（每条含【层级】外部契约|可观测副作用|实现细节、【发现来源】静态读码文件:行|实证、【处置】必须保留|允许变更+理由）+ **意图与历史动因笔记**（防止删掉有意为之的逻辑）。落盘 `.ctbz-record/methods/<node>/<run>/<task>/behavior-inventory.md`
2.5 **基线固化**：对【必须保留】行为用旧实现跑出输入→输出/副作用快照（golden），落同目录 baseline/；旧模块无测试时按"必须保留"条数逐条补最少量测试，不全量补测；判定【允许变更】的副作用剔除出等价范围
3. **新方案设计**：服务整个项目 + 连接上下游；以行为清单为对照
4. **反审**：主对象=方案质量（遗漏/冗余/是否真服务整个项目）；增补视角拆两指标——清单自洽率（reviewer 可判）/清单完备性（步骤 2 作者+基线证据负责，reviewer 只做抽样反例挑战）；反审输出="对【必须保留】条目的反例清单"，覆盖率 100% 硬门取消
5. **表达 + 叫停窗口**：表达=最后一次廉价叫停点；自动重构经 ServerChan 推送一次"方案已表达，N 分钟后开干，回消息即暂停"
6. **派发**：同模块重构=单 Agent 单 worktree 单 write-set；≤5 并行仅适用于已物理拆分的可独立编译单元，单元接口定义与实现同 write-set、不共享文件；写并发守 maxParallelWriters；"逻辑允许范围内"不为凑数强拆
6.5 **集成**：备份旧模块（原文件副本或 tag）→ 原子替换 → 失败回退到备份，汇报明示"已回退/已替换"
7. **行为对照验证**：【必须保留】条目逐条 vs 基线快照
8. **停机条款**：发现超边界行为（暗藏依赖/隐含副作用）→ 该模块置待确认落盘（manifest+dashboard）、自动模式 ServerChan 推送、不等待、其余继续；dirty worktree 保留
9. **汇报**：行为清单对照结果 + 留删清单（删除需用户授权）

## 知识库接口（1.7.0）

**构建**：`草台班子 构建知识库`（幂等）→ 建 `~/Documents/.ctbz/{版本}/知识库/`：常用.md（预置"知识库使用法"）、目录.md（每条一行：标题（触发：词1|词2）→ 分区文件#锚点）、建模.md/业务.md/数据.md/案例.md（单类一文件；60 行限制仅约束词典型整读候选，流程型强制锚点分段）、待批区/（每条一文件）、自记库-YYYY-MM.md。种子首批 5 层：PC=app_ssid4、老客=is_new 2、FPD5_P1 默认标签、样本口径、成熟门禁。

**三库信任档**：正式库（用户批准，可直接引用须标注来源）> 待批区（引用标"待批"）> 自记库（标"未经验证，仅作线索"，禁 rule/指令性句式）。互斥时正式库优先。

**条目格式**（头部=触发词唯一事实源）：`【触发词】…|…（每条≥2 形态别名：代码名+用户语）【类型】fact|experience|rule（自记禁 rule）【scope】通用|本机【有效期】…【需现场核验】…【来源】日期+确认人|AI自记未确认【风险】高|中|低`，⚠易错点正文优先浮出。

**读点协议（先分析后带缺口查）**：①分析任务原文→与触发词表求交集（脚本确定性归一化：小写/去下划线/全半角；零命中时 AI 同义扩展回填别名槽）→常用.md 只作排序器，候选在目录全量并集上排序→命中的词典型条目 30 秒精读；②出计划前读流程型全文；③执行中遇字段/路径查事实型（子 Agent 无库权限时按契约回传缺口，父进程查库回填）；④完成反审沉淀：随手记→自记库，够格→待批区+报用户。**零命中三分支**：缺口阻塞任务定义→问用户限一次；不阻塞→通用能力开工+缺口进待确认项；反审确认库缺→写自记库+检索缺口台账。**同条重读≥2 次**→库病诊断进自记库（不进意见箱）。**引用即核验**：【需现场核验】项自动进任务核验清单。

**冲突闭环**：知识库 vs 现场 → Agent 自查（用错/过期/前提变化）→ 查不出才问用户（每冲突点限一次；显式问"是库用错了还是知识该更新"）→ 裁定回写。**无人值守分支**：高风险冲突（样本/标签/口径/远端写入）→ 该点记待确认、跳过继续其余；低风险→现场证据优先+记录待确认继续。

**晋升与治理**：待批→正式仅由用户显式命令 `草台班子 批准知识 <id>`（无自动转正）。常用.md 人工置顶（不搞自动晋升），库指标存 `.ctbz/库指标.json`（版本目录外）。冷归档：自记月文件超 40 条或条目命中 3 次未被引用→移入归档/退出检索。过期检测挂检索命中路径（命中即查有效期，过期标"疑似过期"降权）。检索/写入脚本：`node <skill>/scripts/知识库.js add|search|index|approve|conflict`。

**模型健康账本**：`~/Documents/.ctbz/模型健康.json` 记录"模型→冷却截止时刻"（从限额类报错的重置时间戳解析写入；用户口头反馈也可写）。派发（initialize select）前读账本过滤冷却中的模型，跳过不派；账本条目过期自动失效（无需清理）；**不探活、不与调用规则.json 混写**（那是成本偏好，这是健康事实）。
**边界**：知识库在 `~/Documents/.ctbz/`（用户级、按版本目录），**不进 git/发布包**，各机用"构建知识库"自建；存量为旧目录时入口前跑 version-check 提示搬移（保留原目录+标记已迁移，删除需用户逐项确认）。自动模式下遇必须问用户的问题→ServerChan 推送（SendKey 初始化时检查并发测试消息；未配置则跳过推送按待决机制处理）。

按阶段读本包 [Matt 适配方法](methods/matt/recommended.md) 和 Superpowers 索引，不执行上游 setup、hooks 或自动发布流程。免配置仅指流程方法：模型派发仍须合法初始化，业务确认、权限和浏览器工具要求仍保留。官方 web-gui-tester 可选且不随包分发，缺失时明确报告验证缺口，不伪称通过。已有授权项目把预设版本和覆盖项记入原项目记录，不新增机器配置。

两套上游固定源仓库引用、许可证及快捷升级方法见 [来源升级](references/upstream-updates.md)。ask-matt 属于 mattpocock/skills，并非独立仓库；原始源码仅归档，运行时按需读取 CTBZ 适配方法。

## 内置方法

父会话先读 [方法共享契约](methods/contract.md)，再按当前工作读取 [方法索引](methods/index.json) 中的入口与必要资源。14 项 Superpowers、Ponytail 和 i-have-adhd 已在当前 CTBZ 目录内适配，读取方式与完整阶段映射见 [方法接入](references/methods.md)。不加载原始归档中的 bootstrap、hooks、调度器或脚本，不查找全局同名版本补件。

讨论/设计用 brainstorming，规划用 writing-plans；主会话直做用 executing-plans，独立模块协调用 subagent-driven-development/dispatching-parallel-agents；代码行为用 test-driven-development，异常用 systematic-debugging，评审用 requesting-code-review/receiving-code-review，完成与收尾用 verification-before-completion/finishing-a-development-branch。只读取当前需要的方法，不把 16 项正文全量注入角色。已激活会话中的执行类工作（含小修复）按所有权约束派发团队；用户明确免派发、禁止子 Agent 或未初始化时保留主会话路径。

父会话运行 `node "<skill>/scripts/methods" check` 检查依赖，`list`/`show <id>` 定位方法；`<skill>` 替换为当前安装绝对路径。只读角色从 profile 和任务契约直接 Read 绝对路径，不运行读取 CLI、不写计划或报告、不派生 Agent。方法/模板缺件或哈希漂移时报告本安装错误并保留现场，不静默切换版本。方法产物统一关联同项目/node/run/task 并保存在 `.ctbz-record`。

## 项目入口与主进程阶段

先按 [共享契约](methods/contract.md) 确认目标、不可变条件、用途、验收和当前阶段。纯讨论、提问或评估可以读材料并给判断，不据此实施、创建或改动记录、发布；用户明确要求保存材料时按其范围记录。正在执行中的提问先回答再续作；用户明确更改目标时以新要求为准，旧摘要与代理转发不能覆盖它。

父会话读取当前项目已有的 `.ctbz-record/dashboard.json` 与 `.ctbz-record/记录.md`，核对已确认决定、权威产物、作废版本、正在执行的节点和待办。进入已授权执行且记录不存在时，用 `node <skill>/scripts/dashboard init --workspace <项目绝对路径> --title <项目名> --goal <目标> --mode normal` 建立项目记录；循环研究或循环开发用 `--mode loop`。用户明确要求建立看板或保存讨论记录时也可建立。这不依赖团队模型初始化，简单任务只记录必要事实。详细命令与数据边界见 `references/项目看板.md`。

1.5.0 的任务归属、检查点、回执与成果操作先读 [工作协议](references/dashboard-workflow.md)。一个目录持久保留项目，独立任务用顶层 work 组，各自控制模式、预算和循环。主进程登记 scope owner；已绑定执行事实只能从 manifest 投影，网页和普通 node.upsert 不覆盖它。使用 team-state 的任务先 checkpoint 对账并明确采用当前计划，再派发；暂停/停止或未采用新目标时不能新派发，已有结果仍需接收保留。

普通任务和循环任务均使用项目看板。用户允许启动本地服务时执行 `dashboard serve --workspace <项目绝对路径> --port <空闲端口>` 并提供 URL；绑定默认 loopback，不自动开放公网。现有服务返回端口占用时选其他端口，不停止无关服务。看板关闭不等于研究停止，父会话退出也不等于网页消失。

1. **讨论阶段**：先核对现有材料，将影响目标、范围、业务口径、成本和验收的关键问题集中整理。每个决策点提供 2-3 个合理选项、推荐项和取舍；相互依赖的问题可合并为完整方案。已获授权、已明确或可通过材料查明的事项不反复追问。技术细节由对应模块处理。已授权执行或明确要求保存时，决策写入看板 questions，用户明确选择后记录答案；纯讨论只返回判断，AI 的推荐不能冒充用户确认。
2. **规划阶段**：复杂任务先用几行说明理解，再按下节流程确认设计、验证并拆分，记录输入、输出、允许写入范围、验收和资料路径；明确小任务按下节适用范围处理。指定来源、粒度、时间口径、标签、模型版本和交付形式随任务传递，不静默替换。用户举例不自动缩小范围，简化表达不减少必要交付。树的 group 节点用于汇总；task/experiment 才是可执行工作。独立模块或有明确对象的复核才派子 Agent，不为问明白、对口径、日常记事单设常驻角色。
3. **执行阶段**：派发前检查待决问题、控制请求、依赖和预算；用真实 Agent 回执更新状态、证据与阻塞原因。在开始工作和每个真实检查点用 team-state checkpoint 对账，按实际阅读填写 seenPlanRevision；主会话直做可调用 dashboard checkpoint。不能用定时假心跳伪造存活。网页操作生成带编号请求，父会话用同一 requestId 记录收到、完成或失败；收到暂停先停新派发，在途任务到达实际检查点后才确认暂停。停止禁止自动续跑，新的明确继续请求才恢复。
4. **验收与收尾**：按风险核对成果、测试、适用评审和集成证据，批量与语义任务区分样例检查和必要全量检查。收到纠偏先核实，标出失效假设、产物和结论，重验受影响部分。记录实际方法、踩坑、结论、未解决事项与下一步；替代检查不冒充原目标完成。子 Agent 返回模块事实，父会话确认后写记录。team-state 的 finish-run 只结束该 run，全部目标达到原定验收且无阻塞问题后再结束项目。普通快报直接输出；完整受众材料用汇报导出或 reporter，主交付不默认附全部过程资料，不自动发送外部消息。

### 设计、原型与实现流程

**适用范围**：有新设计不确定性时走完整流程；已验证任务复用仍适用的结论，小修复做必要测试即可。执行中发现新的关键假设，暂停受影响任务并回到设计验证，无关且已授权任务可继续。用户可自行选择各环节技能，也可明确采用推荐预设免配置使用；未采用不强行绑定，拒绝推荐不阻止普通授权任务。按当前阶段读取所选方法。

1. **访谈**：使用用户绑定的访谈技能，沿设计树逐轮澄清，每个未决问题给推荐答案与取舍；事实先自查，已裁决事项不重问。
2. **裁决落档**：父会话先咨询设计材料位置，未指定默认项目 `./docs/design/`，已有选择不重复询问。保存裁决及重大取舍 ADR，保留选择和理由；设计材料引用同一权威版本，执行 manifest、看板与过程证据仍按原记录协议保存。
3. **统一设计稿与验证标准**：合并为一份权威设计稿，附旧规则替代清单、真值缺口及关键假设；接口与模块方案比较后择一。原型开始前明确验证问题、方法和通过标准，覆盖适用的前端、后端、接口、数据、状态、权限、异常处理与关键技术风险。
4. **原型验证**：在独立目录做最小可运行原型，不改生产代码。核心业务至少跑通一条完整链路，阻塞实现的高风险假设全部有证据；其他未验证细节列明并纳入后续任务与正式验收。有前端时验证前后端联通、真实交互并留截图；纯后端验证对应的完整业务链路，不强制 UI。mock、模拟数据或截图不能证明真实集成。
5. **双层确认**：执行者提供技术证据，由父会话复核；业务效果及适用的使用体验由用户查看原型结果并确认。两层均通过才可回补定稿并拆分实现；任一未通过回到设计、调整并重验，等待确认不算通过。
6. **回补定稿**：依据验证结果回补统一设计稿、正式验收条件和实施方案。统一稿持续更新，记录原设计、证据、调整及影响范围；业务行为、范围或体验变化由用户确认，变更按影响范围重验，核心链路受影响就重验该链路。原型代码仅经评估后选择性复用，明确保留、重构或替换；保留部分仍须正式测试与验收，原型通过不替代正式测试。
7. **面向 worktree 拆分**：任务列明依赖、接口契约、write-set 与验收条件，引用同一已验证设计版本。共享接口、schema、config 各有唯一 owner；必要前置任务完成后再派发依赖任务。按可隔离写集合决定并行或串行，不强制并行。拆分完成后提醒用户另开独立会话安排开发，建议以经济性为主；交接设计、正式验收和任务计划的绝对路径、版本、依赖及未解决项。当前规划会话不自动进入⑧；用户明确改为同会话继续时尊重该选择，泛称自动模式不自动取消交接。经济优先不减少验收或擅自切换模型。
8. **独立 worktree 开发**：每个并行写任务使用独立 Git worktree 和分支，从同一确认基线建立；依赖成果就绪后先对齐基线再执行。遵守 write-set、现有派发协议、总并发与写并发预算及暂停/停止控制；预算或前置条件不满足时暂停相应派发。
9. **集成验收**：按依赖顺序集成，执行正式验收与跨模块回归，核对完整链路及原型阶段遗留的未验证项。未集成或 dirty 工作树保留，清理按 references/worktrees.md 的原协议取得授权；收尾沿用上节验收与收尾协议。

## 循环研究与开发

每轮推进一个明确研究方向，该方向内部可以并行分解。初次讨论记录目标、停止条件和轮次或时间预算，并建立当时已发现的方向。候选 score 是相对优先级判断，记录理由；不是成功概率或项目完成度。候选依赖满足且未阻塞才可执行，汇总父节点不与子节点重复计权。

每轮先 `round.start`，保存当时的排序与选中节点；默认选择最高分的可执行候选。完成验证后记录 result、evidence、method、pitfalls 和 outcome。证明方向不可行也可以完成，outcome=rejected；执行中断或没有得到证据不能冒充 completed。只为新的明确待验证问题增加子节点。最后 `round.finish` 记录该轮总结和后续方向，再重评剩余候选。没有候选、全部阻塞、预算耗尽、达到目标或用户请求停止时暂停；不为了维持循环而凭空扩展节点。

每次真实节点变化和每轮收尾都落盘，不能等整个循环结束才记录。网页按 completedRound 显示当前查看轮次的浅绿色和以前轮次的深绿色；未完成为灰色，进展状态与结论分开。持久化只提供可恢复的检查点，不承诺 ZCode 父会话断流后的自动继续。

## 两级知识

当前版本按项目管理 knowledge。已确认知识 tier=confirmed 优先在适用范围内使用；AI 总结 tier=experience 可参考但注明来源、范围、可信度与未确认状态。新经验可自动整理，不能自动升级。只有用户在网页明确确认，或用户已经明确授权该条知识时由父会话记录 user 事件，才可 knowledge.confirm。知识与现有证据冲突时提出修订，不静默覆盖用户确认内容。经验被反复引用、任务完成或模型高置信均不构成用户确认。暂不进行跨项目全局知识扫描或自动发布。

## 一句话初始化

用户说“草台班子初始化”时，父会话自动执行初始化入口，不要求用户手工拼命令。先运行 `initialize status`；若未选择状态目录，询问三项：1. 当前用户 Documents 下的 `.ctbz`；2. 用户指定的绝对目录下的 `.ctbz`；3. 稍后再选（先不创建团队状态）。默认推荐 Documents。选定后父会话调用 `initialize prepare`，展示本机模型候选、角色×模型数量与冲突，确认后生成；若本机没有可用候选，保留父会话模式并报告阻塞。

prepare完成后提示“请新开会话并再次说草台班子初始化”。新会话自动读取状态，检查已加载 profile；若宿主已加载则调用 `initialize activate`，通过后写入 `.ctbz/已初始化.txt`（内容为当前时间）和结构化状态。未加载则明确等待，不伪称初始化完成。状态目录选择、初始化状态和调用规则均按每台电脑独立持久化。

已 prepare 的机器上新会话只需一步激活：把当前宿主 Agent 工具列表中的 team profile 精确名称写成 JSON 后执行 activate，不得重复 prepare。status 报 drift 时先核对 初始化状态.json 的 installRoot 与指纹：installRoot 非本安装即为副本劫持，按重新 prepare 处理；installRoot 正确而指纹瞬时不一致多为宿主刚重写配置，稍候重试 activate 即可。

支持目录：macOS 默认 `~/Documents/.ctbz`；Windows 优先 `%OneDrive%/Documents/.ctbz`，否则 `%USERPROFILE%/Documents/.ctbz`；Linux 优先 `$XDG_DOCUMENTS_DIR/.ctbz`，否则 `~/Documents/.ctbz`。用户选择“稍后”时，父会话仍可直接处理主会话任务；需要子 Agent 时要求先选择目录并初始化。

## 所有权

父会话是唯一调度者，决定任务使用哪个角色；包工头决定该角色使用哪个已加载模型。子Agent不得派生Agent。角色唯一来源是本版本角色清单.json；不硬编码角色数量、厂商或模型名字。角色×选定模型初始化，每模型只用最高受支持推理档位；未知档位不可猜测。

完成快捷初始化并激活后，任务执行一律派发给 ctbz 团队 profile：先 `initialize select` 按角色与调用规则取得合法 profile，再真实派发并接收回执。已激活会话中的执行类工作（写文件、改代码、跑验证命令）默认派发团队，包括小修复；general-purpose、Explore 等宿主通用 agent 不得替代团队角色，也不得与团队角色混用承担同一任务。主会话直做仅限三类：纯讨论与问答、用户明确说"不用派/直接做"、以及未初始化或 select 拒绝时向用户报告阻塞（此时不得改用通用 agent 降级）。未激活、select 拒绝或 profile 未加载时停止派发并提示新会话激活。

## 未初始化也可使用

需要核对团队可用性时运行 scripts/initialize status；纯讨论不用先做机器初始化检查。未初始化时可讨论、规划或由父会话直接处理授权任务，建议初始化但不强迫。需要团队派发而无合法角色时明确阻塞，不猜profile。用户禁止子Agent时主会话处理，不伪造agentId。

## 初始化

完整步骤与参数见references/初始化.md。setup和reconfigure都使用同一initialize prepare流程，不再按旧访谈硬编码生成模型。模型团队状态使用用户选定目录，宿主profile根~/.zcode/agents；项目看板独立存入项目 `.ctbz-record`。

1. 使用discover-config安全发现模型，不读取credentials.json，不输出密钥或端点。父会话展示选定模型与生成数量，用户指定时以指定清单为准。
2. prepare生成全部角色组合及兼容team配置；重跑相同输入不重写。自定义profile冲突拒绝，旧受管文件备份。
3. 等待新会话，将当前宿主Agent工具列表中的精确profile名称写成JSON，再activate。禁止把磁盘列表冒充已加载列表。
4. 激活通过后写初始化状态.json和已初始化.txt时间。标记是可读提示，不单独作为有效性证明。激活证明配置一致，不代表真实模型在线。

## 包工头与文件规则

每次派发前调用initialize select，传角色、父模型精确引用、当前session及宿主加载列表。默认仅同provider，不根据模型名猜厂商。调用规则.json默认临时规则为空，无任何活动随发布包分发。

用户说某时间段优先某模型时，编辑本机调用规则文件；规则需要起止时区、优先级、模型精确引用。到期不生效但记录保留。每次select重新读文件并返回哈希，无上下文缓存覆盖磁盘；用户要求刷新时reload。格式错误报错，不沿用旧规则。新增未初始化模型需prepare及新会话激活。

## 运行闭环

select返回team=ctbz与stateDir，父会话使用同一team-state init-run/update-task记录任务；初始化清单的profile名称与route直接兼容，不再拼短名。角色缺失、版本漂移、未加载、规则引用未知模型均停止对应派发。

派发前记录任务契约、目标、输入、write-set、验收和必要背景；并行代码写任务使用worktree，各自隔离。未初始化父会话任务仅记录本地任务文档，不伪造旧team-state记录。

失败分类按references/failure-policy.md：断流预算内用SendMessage恢复原Agent，再排除失败profile重选；权限拒绝与代码错误不靠切模型绕过。重试、总并发、写并发仍需父会话按team配置核对，本版不宣称宿主强制调度隔离。维护批次重prepare在profile名称集合不变时自动携带已激活会话；旧generation悬挂的run用 `adopt-run --state-dir <旧代state> --adopter-state-dir <当前state>` 跨代接管（旧manifest冻结为cancelled，续跑manifest重绑当前代并留溯源），终态run不可再接管。

完成前检查测试、评审与集成证据，使用team-state完成记录；worktree按references/worktrees.md清理，未确认集成或dirty时保留。team-state 接受任务变更后投影到项目看板；若返回 dashboard.synced=false，原任务记录已保存，但看板未更新，须报告并在修复记录问题后重试同步，不能把旧看板当最新状态。

## 安全与记录

不修改provider配置、凭据、宿主数据库或应用。安装到用户目录、真实模型探测或计费调用须有用户授权；已有会话授权按范围沿用，不反复询问。不自动commit/push，除非用户已授权 Git 管理或提交。JSON 项目记录是看板状态依据，Markdown 是人类可读记录；错误不能隐去。机器配置、密钥和调用规则不进入看板、导出或发布包。

CTBZ 汇报读取本包 [i-have-adhd](methods/i-have-adhd.md)，代码取舍读取本包 [Ponytail](methods/ponytail.md)。缺件时明确报告依赖错误并用简洁文本说明当前状态，不能因此隐去错误，也不回退全局技能。安装前保留用户自定义内容并说明能力差异。看板提供循环协议与状态，实际执行仍由宿主父会话承担。
