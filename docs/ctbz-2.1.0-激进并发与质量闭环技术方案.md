# ctbz 2.1.0 激进并发与质量闭环技术方案

## 1. 目标

在 2.0 治理闭环基础上，建立“主 Agent 负责设计与最终裁决，子进程负责执行与质量复核”的默认运行模型，提升独立任务并行度，同时避免共享文件冲突、局部绿灯和实现偏离技术设计。

## 2. 已确认问题

1. 当前并发主要按阶段或角色组织，不能按依赖就绪即时补位。
2. `maxParallel` 尚未区分读、写、评审资源，调度粒度偏粗。
3. 并发写入边界依赖协议，CLI 对共享文件 owner、写并发和回执完整性约束不足。
4. 子进程质量检查尚未形成“实现内容复述→技术文档交叉验证→打回重做→复检”的强制闭环。
5. 主进程容易在侦察后直接修改文件，未把执行类操作稳定交给子进程。
6. 当前验收证据仍可能出现模块通过但整体链路未通过的情况。

## 3. 核心原则

- 主 Agent 只负责需求理解、蓝图、详细计划、方案裁决、派发、集成决策和最终检查。
- 除设计计划外，开发、测试、文档、脚本、发布准备等执行类操作默认派发子进程。
- 每个写任务使用独立 worktree、独立分支和明确 write-set。
- 同一可编译单元只能有一个写 owner；接口、schema、配置与实现不得拆到互相等待的任务。
- 并发依据依赖和资源动态调度，不为凑数强拆任务。
- 质量检查必须由未参与该任务实现的子进程完成。
- 检查结论必须有可核对证据；不一致即打回，不得由主 Agent 口头豁免。
- 主 Agent 最终检查不能替代子进程独立检查，子进程通过也不能替代整体验收。

## 4. 运行角色

| 角色 | 职责 | 是否写文件 |
|---|---|---|
| 主 Agent | 设计计划、蓝图、派发、裁决、集成、最终检查 | 仅设计产物；执行类改动默认不写 |
| 开发 Agent | 按技术文档实现指定 write-set，运行局部验证 | 仅授权 write-set |
| 测试 Agent | 编写或运行测试，回传证据 | 按任务授权 |
| 质量检查 Agent | 复述实际内容并与技术文档逐项交叉验证 | 默认只读 |
| 集成 Agent | 按依赖顺序合并并运行组合验证 | 集成 worktree |

## 5. 任务契约

每个子任务必须包含：目标、输入、技术文档版本、write-set、禁止修改范围、前置依赖、验收命令、完成标准、回滚点、回执格式。

任务必须绑定唯一 `planVersion`、`moduleId`、`taskId` 和基线 commit。技术文档变更后生成新版本，旧任务不得继续使用旧文档静默执行。

## 6. 动态并发调度

### 6.1 资源池

调度器维护三类预算：

- `readParallel`：侦察、测试运行、只读评审。
- `writeParallel`：独立 worktree 中的写任务。
- `reviewParallel`：独立质量检查。

另设总并发 `maxParallel`、模型健康过滤、失败重试预算和单项目 `maxParallelWriters`。

### 6.2 事件触发

任务状态采用 `blocked → ready → running → produced → reviewing → rework → approved → integrated`。依赖满足、接口冻结或 Agent 释放资源时立即触发调度，不等待整批阶段完成。

### 6.3 冲突控制

共享接口、schema、配置和生成文件登记唯一 owner。调度器发现 write-set 重叠、基线漂移或 owner 缺失时，暂停冲突任务并写入 manifest；禁止静默覆盖或自动择一。

### 6.4 失败处理

失败分为断流、权限拒绝、环境失败、实现缺陷和契约偏离。断流可在预算内恢复原 Agent；实现缺陷进入回修；契约偏离必须回到开发 Agent；权限拒绝不得靠换模型伪造成功。

## 7. 强制质量闭环

### 7.1 开发阶段

开发 Agent 读取固定版本技术文档，在授权 worktree 完成实现和局部验证，提交以下回执：变更文件、行为说明、测试输出、未完成项、风险和基线差异。

### 7.2 第一轮质量检查

质量检查 Agent 获取：原始需求、蓝图、技术文档、开发 diff、测试输出和任务契约。它必须先独立写出《我看到了什么内容》：逐文件说明实际新增、删除、修改的行为、接口、数据流、权限和副作用，并标注证据位置。

### 7.3 交叉验证

检查 Agent 将《我看到了什么内容》与技术文档逐条比对，输出状态表：

| 条目 | 文档要求 | 实际内容 | 证据 | 结论 |
|---|---|---|---|---|
| 行为/接口/约束 | 原文条目 | 实际实现 | 文件与行号、命令输出 | 一致/不一致/缺证据 |

检查范围包括功能行为、接口契约、错误处理、权限边界、并发隔离、测试覆盖、性能安全和文档同步。

### 7.4 打回规则

出现任一“不一致”、关键项“缺证据”、越界写入、测试未通过或技术文档未覆盖的新增行为，状态置为 `rework-required`，生成带位置、触发条件、影响和修复建议的缺陷清单，退回原开发 Agent。不得直接由主 Agent 改代码代替回修。

### 7.5 回修与复检

开发 Agent 只处理缺陷清单及必要关联改动，保留原 worktree 和新 diff。质量检查 Agent 使用新鲜快照再次生成《我看到了什么内容》并复核；连续两轮无新增证据才允许进入 `approved`。复检仍失败则继续回修；若发现计划或接口错误，升级到主 Agent 重新裁决计划。

### 7.6 主 Agent 最终检查

主 Agent 只在所有模块 `approved` 后进行最终检查：核对原始需求与蓝图、集成 diff、组合测试、跨模块接口、异常链路、未验证项和回滚点。主 Agent 必须输出最终验收表，不能只引用子进程“通过”。

## 8. 数据与命令接口

新增或扩展 manifest 字段：`planVersion`、`moduleId`、`taskId`、`baselineCommit`、`writeSet`、`owner`、`reviewer`、`reviewRound`、`reviewArtifact`、`reworkCount`、`evidence`、`status`。

建议命令：

- `dashboard work.create`：登记工作组与蓝图版本。
- `dispatch ready`：按依赖和资源池派发可执行任务。
- `review package`：生成质量检查材料包。
- `review submit`：提交《我看到了什么内容》和交叉验证表。
- `rework start`：按缺陷清单退回原开发任务。
- `review approve`：写入独立检查证据并放行集成。
- `integrate verify`：按依赖顺序集成并运行组合验收。

CLI 必须拒绝：无技术文档版本的执行任务、无独立 reviewer 的通过、reviewer 与 developer 相同、write-set 重叠、缺少证据的 approve、未通过模块直接集成。

## 9. 验收标准

1. 三个以上互不重叠模块可同时运行，依赖任务能在前置接口冻结后即时启动。
2. 任意 write-set 重叠均被阻断并留下 manifest 证据。
3. 开发偏离技术文档时，首轮检查能稳定识别并打回。
4. 回修后复检能识别新增回归；至少一轮完整“开发→检查→打回→回修→复检”通过。
5. reviewer 无写权限且不读取开发 Agent 的主观解释作为唯一依据。
6. 模块全部通过后，集成验收能发现跨模块接口和异常链路问题。
7. 主 Agent 最终验收表包含原始目标、实际行为、测试证据和未验证项。
8. 现有测试全部保持通过，并新增调度、冲突、回修和复检回归测试。

## 10. 实施顺序

1. 扩展 manifest、任务状态和 reviewer 回执数据结构。
2. 实现三类并发预算、依赖就绪事件和 write-set 冲突阻断。
3. 固化 review package 与《我看到了什么内容》模板。
4. 实现打回、原任务回修、复检和轮次证据链。
5. 接入 dashboard 状态投影和失败分类。
6. 增加隔离 CLI 回归测试，再进行真实团队链路验收。

## 11. 暂不突破的边界

不允许多人同时写同一可编译单元；不允许用增加 Agent 数量替代任务可拆分性；不允许质量检查 Agent 修改被检查代码；不允许局部模块通过冒充整体完成；不允许以模型切换掩盖权限、环境或契约问题。

## 12. 开工授权门（新增）

### 12.1 设计目的

主 Agent 在执行期间保持可对话、可裁决、可止损。普通模式和自动模式不得因计划完成、反审通过、倒计时到期或子进程空闲而自动开工；只有用户明确指令或模式自身的明确授权，才能从计划阶段进入执行阶段。

### 12.2 模式规则

| 模式 | 计划完成后 | 开工条件 |
|---|---|---|
| 普通 | 停留在 `planned-awaiting-start` | 用户明确说“开始执行/开工/执行这个计划”等等价指令 |
| 自动 | 停留在 `planned-awaiting-start` | 用户在进入自动模式时已明确授权自动执行；后续按计划自动推进 |
| 快速 | 可直接进入执行 | 保留快速模式已有授权和必要自检 |

“继续”“好的”“看到了”等确认性回复不视为开工指令，除非上下文明确指向执行动作。计划有修改、反审有新增阻塞或用户改变范围时，开工授权失效，必须重新确认。

### 12.3 计划停留内容

进入 `planned-awaiting-start` 时，主 Agent 必须给出可审阅的计划包：目标与非目标、模块拆分、依赖图、write-set、并发预算、技术文档版本、反审结果、风险、验证方案、回滚点、预计子进程队列和未决问题。此阶段允许继续对话、回答问题、修改计划和重做反审，不创建执行型 worktree，不派发写任务。

### 12.4 授权记录

开工指令写入 `startAuthorization`：原文、时间、会话、适用 `planVersion`、适用模块范围、模式和授权状态。仅当授权版本与当前计划、蓝图和反审快照一致时，调度器才可将任务置为 `ready`。授权不得扩大原计划范围；新增模块、外部写入、发布、推送等高风险动作仍需单独授权。

### 12.5 CLI 门禁

新增状态和命令约束：

- `planned-awaiting-start`：计划已形成，等待明确开工。
- `start --plan <version> --scope <...>`：记录用户明确授权并开启调度。
- `dispatch`、`work.create`、写入型 `run`：无有效 `startAuthorization` 时拒绝。
- `status`：显示等待原因、计划版本、反审状态和授权范围。
- `pause`：立即阻止新任务，保留运行中任务现场；`stop`：按停机条款执行。

### 12.6 与子进程优先原则的关系

开工授权只授予“可以开始执行”，不改变执行分工。授权生效后，开发、测试、文档和发布准备仍默认交给子进程；主 Agent 保持对话、调度、裁决和止损能力。主 Agent 只有在低成本控制动作、紧急回滚或最终裁决时直接操作。

### 12.7 验收标准

1. 普通模式完成计划后，未收到明确开工指令时，零写任务被派发。
2. 自动模式只有在进入模式时已记录明确授权才可自动开工。
3. 快速模式不被该门禁阻塞，但仍执行必要自检和实际验证。
4. 计划、范围或反审快照变化后，旧开工授权自动失效。
5. “继续”“好的”等模糊回复不会误触发开工。
6. 主 Agent 在等待期间能继续回答用户问题并修改计划，不丢失上下文。

## 13. 反审协议补强：目标覆盖与长期短板

每次计划反审必须明确回答以下两个问题，并将答案写入反审记录：

1. **当前这份计划是否满足刚才提到的所有需求？**
   - 逐项列出需求、对应计划条款、验证方式和证据状态。
   - 任何未覆盖、部分覆盖或依赖未来实现的内容必须标明，不得以总体描述代替逐项核对。

2. **整个工作要达成什么目的？更新完成后还有哪些短板可以提升？**
   - 用一句话说明最终要解决的真实问题。
   - 区分功能完成、问题解决和实际可用三个层次。
   - 列出本次范围外但已发现的后续短板，避免把本次计划误报为终局方案。

### 13.1 反审输出格式

反审 Agent 必须提交“需求覆盖表”和“目的与剩余短板表”，并给每项标记 `通过/部分覆盖/未覆盖/缺证据`。出现关键需求未覆盖、真实目的不清或剩余短板被隐瞒时，计划不得进入方案裁决。

### 13.2 与既有 ctbz 规则的关系

这不是另起一套反审体系，而是补充现有 ctbz 反审硬门。现有规则来源于：

- `skills/ctbz/SKILL.md`：规定所有计划实施前必须反审，按规模分级，并覆盖需求一致性、架构合理性、测试完整性、边界条件、性能安全和用户体验。
- `skills/ctbz/references/unified-workflow.md`：规定主路径中的计划反审、模块反审、集成反审和最终蓝图验收，以及独立审查、证据、反例、回修和升级规则。

本补强将“是否满足全部需求”和“完成后还有什么短板”提升为每次计划反审的显式必答项；不改变既有独立审查、证据和回修要求。
