# ctbz 四项损失的补齐方案

- 日期：2026-09-21
- 对应：`ctbz-迁移dsh-评估-20260921.md` §4.5「不注册会损失什么」
- 结论：**四项全部可解，其中"角色降级"可完全逆转**；四项的最终收敛形态是**把 ctbz 做成一个 dsh bundle 插件**。

---

## 0. 结论表

| # | 损失 | 能否解决 | 方案一句话 | 成本 | 残留缺口 |
|---|---|---|---|---|---|
| ① | 派发前统一预检 | ✅ 能（软/硬两条路） | 探针脚本对候选模型逐一 8-token 探活并抓 `credit`/限额错误；软=开工前跑一次，硬=`PreToolUse` hook 阻断未过检的派发 | 60–100 行 | workflow 的 `agent()` 不经过工具调用，hook 拦不到；脚本路径须自觉调用 |
| ② | 冷却/限额模型过滤 | ✅ 能 | 健康账本照旧（现有 `模型健康.js` 解析重置时间戳的逻辑不变），过滤逻辑放进**选型函数**；账本更新由①的探针顺带完成 | 小（复用现有脚本） | 静态白名单只在新会话生效，无法分钟级动态改，只能脚本层过滤 |
| ③ | 安装指纹/漂移校验 | ✅ 能，最省 | 该机制本就宿主无关：保留 `dependencies.lock.json`/`部署基线.json`/`发布检查.js`，把扫描对象从"宿主 agents 目录"改成"ctbz 资产 + preset 目录" | 小（改路径） | 不再有"宿主加载名单"可对账（因为不再有加载名单） |
| ④ | 角色降级为配置条目 | ✅ **能完全逆转** | 写一个薄插件注册 `ctbz_dispatch(role, task, model?)`，内部直调 `ctx.subagents`，把 `persona`/`toolFilter`/`agentOptions` **按每次请求**传入 | 中（cordis 插件级） | 插件操作需 `danger-full-access`；装新 JS 需重启进程 |

---

## 1. 为什么 ④ 能逆转（关键证据）

**内置工具**只把 `persona`/`toolFilter` 放在**实例配置**层（preset 里一个实例=一个固定角色），所以看起来角色被"配置期定死"。

但**服务层**不是这样：

| 证据 | 内容 |
|---|---|
| `dsh-subagent/lib/index.js` | 服务是一个具名提供方注册表，暴露 `start()`、`startContinuable()`、`listChildren()`、`listDescendants()`、`interrupt()`、`interruptByParent()`、`sendMessage()` |
| `dsh-subagent-in-process-driver/lib/index.js:174-175,186` | 子 agent 创建时**逐请求**转发：`persona: request.persona`、`toolFilter: request.toolFilter`、`agentOptions: resolveChildAgentOptions(parent, request.agentOptions, childDepth)` |
| `dsh-subagent-spawn-in-process/lib/index.js` | `spawn` 后端声明**全部**启动期能力：`agentOptions` / `outputSchema` / `depthLimit` / `toolFilter` / `persona` |
| `dsh-subagent/lib/index.js:551-556` | 实现：`childCtx.systemPrompt.section({name:"deployment:persona-prefix", text:composition.persona})`、`childCtx.tools.restrict(composition.toolFilter)` |
| `dsh-subagent/README.zh.md` | "**直接调用服务的调用方**仍自行提供可选的请求深度" → 服务可被工具之外的调用方使用 |

**推论**：写一个插件工具 `ctbz_dispatch`，在工具实现里调用服务并逐请求传 `persona`（角色指令）、`toolFilter`（工具白名单）、`agentOptions`（模型），就能得到：

- **运行时任意角色**（角色库从 `角色清单.json` 生成，随用随起）；
- **宿主强制的工具白名单**（`tools.restrict()`，不是 prompt 自律）；
- **逐次钉模型**（含本次定下的 5 模型 4 阵营名单）。

即：不仅补回 ZCode 的能力，还比 WSL 时代（104 个静态 profile + 派发前 select）更简洁——**角色从"预生成文件"变成"一次带参数的调用"**。

插件开发有官方路径可依：`dsh-plugin-manager`（装包 spec 支持 npm/git/本地路径/tarball，包声明 `dsh.bundle.patch` 即成 bundle）、`dsh-skill`（`ctx.skills.register`）、`dsh-system-prompt`（`ctx.systemPrompt.section`）；"创造模式" preset（`presets/cordis/`）自带 `cordis-plugin-development` 技能与运行时检查。

## 2. 逐项方案

### ① 派发前统一预检（preflight）

**做什么**：读 `~/.dsh/settings.yaml` 声明的 provider/model + 凭据库 refs → 对每个候选模型发一次最小请求（`max_tokens=8`，中文单词提示）→ 输出一张"可用 / 不可用（附错误与限额重置时间）/ credit"表。
- 已有原型：2026-09-21 本轮实测 5 个模型（M1–M5）全部通过，并抓到 `credit` 0 / 0.01 / 0.1，可作模板。
- 建议落点：`scripts/preflight.mjs`（profile 参数化，支持 `--models M1,M2,...`、`--json`）。

**软路径（自觉调用）**：项目开工或每轮循环开始时跑一次，结果落 `.ctbz-record/`，写进派发契约的"台账编号清单"旁边。
**硬路径（机械阻断）**：dsh 的 hook 桥支持 `PreToolUse` 阻塞工具或 `ask`，退出码 2 = 阻塞（证据 `dsh-hooks-claude-code/README.zh.md`）。把 checker 挂在 `subagent`/`spawn_teammate` 工具名上，未过检的派发直接被拦。

**残留**：workflow 的 `agent()` 不经过工具调用，hook 拦不到 workflow 内部派发 → workflow 路径依赖脚本自觉（可在脚本第 0 阶段调 preflight）。

### ② 冷却/限额模型过滤

**做什么**：健康账本继续用（`~/Documents/.ctbz/模型健康.json`；`scripts/模型健康.js` 的限额重置时间戳解析逻辑完全保留）。
- **更新**：由①的探针顺带做——curl 拿得到完整错误体，可直接解析"限额将在 X 重置"。
- **过滤**：放在**选型函数**里（路线二 workflow 脚本的天然位置）：先读账本剔除冷却中的模型，再按"4 家阵营"规则取样；命中的模型失败则带 `--exclude` 语义滑到同阵营下一个。
- **补强**：`subagent-model-selection.allowedModels` 白名单作为硬边界，只放"允许用"的模型；分钟级冷却靠脚本过滤，不指望改白名单（只对新会话生效）。

**残留**：没有宿主级"过滤钩子"，过滤是脚本的一等公民而不是宿主保证。

### ③ 指纹/漂移校验

**做什么**：这套机制本来就是 ctbz 自有的文件校验，与宿主无关，**不需要重写，只需要换扫描对象**：

| 现有件 | 现在扫什么 | 改为扫什么 |
|---|---|---|
| `dependencies.lock.json` + `发布检查.js` | 安装目录（宿主的 `~/.agents/skills/ctbz`） | 不变（继续校验安装产物） |
| `部署基线.json` 反向漂移检测 | 安装目录 vs 上次部署 | 不变 |
| （新增）preset 校验 | —— | 把 `<dshHome>/.agent-presets/ctbz/` 纳入 lock/基线，部署时一并校验 |

dsh 侧另有一层自带校验可叠加：`plugin-manager` 的 bundle 校验（`inspect` 返回 `not-a-bundle` 等错误码）、`agent-presets` 对 broken preset 的提前拒绝与原因列示。

**残留**：不再有"宿主已加载名单 vs 磁盘 profile"的对账——因为不再有加载名单，这项校验本身失去对象，不是丢了能力。

## 3. 推荐执行顺序

| 步 | 内容 | 风险 | 量 |
|---|---|---|---|
| 1 | ①软预检 + ③改扫描路径 | 零（只读 + 自有资产） | 半天内 |
| 2 | ②挂进选型函数（依赖路线二/一选定） | 低 | 半天 |
| 3 | ④写 `ctbz_dispatch` bundle 插件（角色运行时化） | 中（动宿主进程内代码，需重启） | 1–2 天 |

**收敛形态**：④ 做成后，①②③ 都可以收进插件内部（插件可注册 `preflight` 工具、在 dispatch 内做健康过滤、把角色库与校验一并管起来）——即报告 §7.1 登记的"ctbz 作为 bundle 接入 dsh"从"可选进阶"升级为**这四项损失的正解**。

## 4. 待确认

1. 插件里起子 agent 所需的 `ctx.subagents` 具体调用签名（`start()` 的请求结构体是否要求 `parent`/`signal` 由插件构造）——需一次原型验证，预计半天内出结论。
2. 路线一/二/三 的选定（②③ 的落点依赖它）。
3. 是否接受插件路径带来的两个约束：装新 JS 要重启进程；`plugin_manager` 操作需 `danger-full-access`。
