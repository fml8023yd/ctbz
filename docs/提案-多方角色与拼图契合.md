# 提案：多方角色与拼图契合（待讨论）

提出：2026-09-22｜来源：用户「每一项工作的完工，不应是一个角色单打独斗」（特征开发为例）
状态：**待讨论，未立项**｜关联待办：TD-11

## 一、现状世界观 vs 缺口

| 现有 | 缺 |
|---|---|
| {用户＝领导} + {AI＝骨干} + {AI 派出的反审席位} + {四扇门：平台写/凭据/真值/权限} | **其他人类角色**：用户自己的领导、做模型上线的开发同事、其他同事 |

实测证据：知识库 185 条 / 9 分区，检索 `角色｜相关方｜干系人` 零命中。关于「上线开发同事」的一切，现存记录全是**物的规则**（`BTY-KNOW-4010` 五件套、`4020` 命名门禁、`7030` 注册占位、`7070` 共享模型目录边界），**无一条记录「人」**。

## 二、缺口造成的三件事

| # | 后果 | 表现 |
|---|---|---|
| 1 | 完工定义偏了 | 验收只问「五件套齐不齐、代码可不可复算」，不问「开发同事能不能接、领导认不认口径、同事会不会撞车」 |
| 2 | 假设无标记 | AI 默认「我的口径＝大家的口径」，等于替用户决定他人的事 |
| 3 | 对齐动作无归属 | 「谁去和开发同事对接口」无字段承载 → 用户记得就说，不记得就漏 |

## 三、提案主体：拼图表

| 列 | 填什么 |
|---|---|
| 角色 | 我的领导 / 上线开发同事 / 同事 / **用户自己** |
| 他要什么 | 他的目标与口径 |
| 我给他什么 | 接口：字段 / 表 / 格式 / 频率 / 延迟 / 交付包 |
| 他的约束 | 雷区与前提（命名门禁、注册占位、共享目录边界…） |
| 状态 | `已对齐` / `不适用（附理由）` / `待对齐` |
| 证据 | 用户原话、对方回复、文档结论（`路径:行号`） |

**命门守卫**：无证据只能填 `待对齐（假设：…）`；**假设行不得作为完工依据**。

## 四、完工定义改写

```
完工 = 拼图放下 = 上游口径有据 ∧ 下游接口对齐 ∧ 横向无重复冲突
├ 上游：口径谁给的、哪天、书面还是口头
├ 下游：交付形态 + 排期谁定的
└ 横向：有没有人已经在做、命名/表名占用
```

## 五、三个选项

| 选项 | 内容 | 代价 | 判断 |
|---|---|---|---|
| A 最小 | 只改完工定义（主文一句 + 验收表一行） | 低 | 便宜，但仍是 prose |
| B 推荐 | A + 拼图表 + 机械闸（`派发闸 --level fit`：有「待对齐」→ 不得标完工） | 中 | 把多方对齐变成可检查产物 |
| C 重 | A + 角色视角反审（领导/下游/横向三镜头并入 L1） | 高 | 席位翻倍；AI 扮演人类有编造风险；建议只在项目标「跨角色」时启用 |

## 六、必须提醒的风险

**最大风险不是漏，是 AI 替用户编造他人的立场。**「开发同事应该能接」比不说更坏——拼图表会变成一份整齐的假账。**证据门槛是这套结构的命门。**

另一条：ctbz 把「领导」特殊化了，但用户的世界里领导只是角色之一；建议把**用户自己也写成一行**（既是上游口径的下游，也是下游交付的上游）。

## 七、待裁决（六项）

| # | 决策点 | 推荐 |
|---|---|---|
| 1 | 拼图表放哪 | 项目级一份（同一批角色接口稳定，可复用） |
| 2 | 「已对齐」证据门槛 | 口述可记「口头确认（日期）」，**口径/排期/权限**三类必须书面 |
| 3 | 角色清单谁给 | AI 给候选、用户勾选（防 AI 编造利益方） |
| 4 | 「不适用」防滥用 | 必须附理由且禁「无需对齐」类空话（可机械拦） |
| 5 | 长期「角色口径卡」 | 落知识库待批区，跑几次再转正 |
| 6 | 组织真值（谁说了算） | 并进四扇门的「真值」门，不另开一门 |
