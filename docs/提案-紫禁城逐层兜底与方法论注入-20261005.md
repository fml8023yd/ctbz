## 1. 紫禁城范围界定

紫禁城 = 子进程池全生命周期管理（用户语音中「紫禁城」「Forbidden City」均指子进程/Subagent）:

```
编制(世代/角色×模型) -> 激活(会话绑定) -> 派发(select) -> 运行兜底(状态机)
-> 反审兜底(席位表) -> 健康(账本/预检) -> 观测(检查点/留痕)
```

## 4. 设计草案 A：五层兜底链

| 层 | 动作 | 触发 | 现状 | 提案 |
|---|---|---|---|---|
| L0 | SendMessage 恢复同 agent | 断流 | 已有（failure-policy） | 保留（不换 agent、不换 profile） |
| L1 | 同 profile 重试（预算内） | transient（408/429/5xx/EOF） | 已有 | 保留 |
| L2 | 同角色换模型档（同渠道内，按调用规则顺序） | profile 级失败 | 部分（route 前移） | 明确为「档位梯」，顺序单一真源 |
| L3 | 换渠道/接入点（同模型跨 provider） | auth/config 类（402/401/欠费） | 仅反审席有 | 泛化到全角色：备选渠道声明 |
| L4 | 换 provider/跨编制（角色允许池内） | 渠道级整体故障 | 无 | 新增：声明式备选池 + 独立性约束 |
| L5 | 熔断上报：FAILED_EXHAUSTED + 已试清单 | 全部耗尽 | 有熔断、无清单格式 | 统一「已试清单」格式，明示不静默 |

约束（沿用既有语义）:

1. 分类驱动降级：`auth/config` 降级；`tool/permission`、`task/code` 不切模型；`transient` 先走 L0/L1。
2. 预算封顶：每层恰好一次（席位表先例）；跨层合计沿用 failure-policy 数字（attemptsPerProfile=2、circuitThreshold=3、maxFallbackProfiles=route 剩余）；route 单向不成环。
3. 反审席独立性：降级不得跨阵营；同源降级保留（回执标注 fallback 来源）。
4. 降级即明示：回执/汇报标注「降级使用 X（原因）」。

## 5. 设计草案 B：声明单一真源

现状四份声明并行：角色清单.json（角色）、调用规则.json（顺序/时间窗）、模型健康.json（健康）、反审席位表.mjs（反审降级）。

提案:

1. 将 `lib/反审席位表.mjs` 泛化为「紫禁城席位表」：角色 → 主档 + 备选链 + 独立性标记。
2. 反审席、派发席、闸门、状态机四方共用同一份声明（沿用 2.1.3「runner 与闸门共用」的单一真源模式，消灭白名单漂移）。
3. 世代只回答「有哪些模型可用」；席位表回答「谁先谁后、谁能替谁、谁不许跨」；健康账本回答「谁现在病着」——三者职责分离，运行时合成路由。

## 6. 设计草案 C：可观测与预算

1. 降级事件落盘：`{ts, layer, from, to, reason_class, result}` 追加到派发检查点（`dispatch_checkpoints.jsonl` 先例），补全现有 checkpoint 只记推荐 profile 的空档。
2. 回执字段沿用 2.1.3 先例（`fallbackFrom` / `fallback_reason`），L2/L3/L4 通用化。
3. 会话启动预检结果作为**只读过滤输入**进派发决策（不改健康账本语义——账本仍只记运行期失败）。
4. 编制检查器：对关键角色（planner/reviewer/implementer/tester）校验 ≥2 渠道覆盖，单渠道即告警。

## 11. 对用户方案的反驳与修正

### R1 「维护主 Agent 可用表格」不成立——它是观测出来的，不是维护出来的

| 项 | 内容 |
|---|---|
| 论据 | 工具列表是宿主在会话启动时按扫描规则生成的；重建档位文件只改变「下次会话能扫到什么」，不改变「本次会话已加载什么」 |
| 实锤 | 本会话列表＝48 个当前档（00:55 写入 → 本会话可见，证明新会话会重扫）＋ 17 个退役 team-dev 档（9 月写入 `~/.zcode/agents/backup-2026*/`，至今仍被扫进列表；`find ~/.zcode -name "team-dev-*.md" \| grep -v backup` 为空） |
| 机制 | 未验证：宿主递归扫描 agents 子目录 vs 宿主注册表残留，二假设并存；现象（退役档出现在工具列表）实锤 |
| 修正 | 更名「会话启动观测快照」；动作＝启动时写快照＋对账＋探活，不是「重建 + 有效期」 |

### R2 要防的漂移是双向的，实锤已有

| 漂移 | 状态 | 证据 |
|---|---|---|
| 工具列表 ⊄ 编制表（列表里有编制外的） | 实锤 | 17 个 team-dev-*（dsv4/omen 谱系）在本会话工具列表可见；`ls ~/.zcode/agents/` 根目录 team-dev 计数＝0，仅存于 backup-2026*/ 子目录；当前世代 team.json 无这些档 |
| 编制表 ⊄ 工具列表（编制里有但没加载） | 本批干净 | 48/48 当前档全部在工具列表（逐角色 6 短码核对）；无机械守卫，下批变化即可能漂移 |

### R3 「每天凌晨 3 点重建」错配：重建是事件驱动，定时的只该是探活

| 项 | 内容 |
|---|---|
| 反驳 | 重建应对「编制变化」事件（模型下架/新增/改偏好）；时钟到点不产生新信息 |
| 夜窗豁免 | 凌晨 3 点的唯一好处＝蹭夜窗免费额度（23:00–09:00 夜窗规则先例）；但只需探活（preflight，≤5 请求），不需重建 |
| 二次成本 | 重复重建制造代际噪音（generations/ 已有 5 个世代） |

### R4 「7 天有效期」锚点错了：该锚在会话启动，不锚在时钟

| 项 | 内容 |
|---|---|
| 反驳 | 模型下架/欠费不以 7 天为周期；有效期制造「刚过期而你还以为有效」窗口 |
| 修正 | 档案带观测时间戳为缓存；每次会话启动做实时对账（零成本——工具列表就在眼前）；冲突即刷新。7 天数字可留作「长期不动时的强制复审兜底」，不作主机制 |

### R5 「另找 Agent 验证名单」是递归陷阱

| 项 | 内容 |
|---|---|
| 反驳 | 验证者本身也是编制与加载的产物；它看到的仅磁盘+API，不比主进程多；且名单可疑时它从哪来 |
| 修正 | 验证＝两个零成本动作，由主进程做：①工具列表↔磁盘差集（把列表写 JSON，脚本算差集——activate --loaded 已有先例）②preflight 探活。若封装成 Agent，只是脚本的壳，无智能增量 |

### 14.2 「三份表合并为路由表」讲解（用户未听懂项）

| 反审席位表.mjs | 技能包 | 4 反审席主档 + 备选降级 | 反审直连 + 派发闸 |

问题：同一件事（谁先用、谁备用、谁不许换）分三处写，改一处漏两处——2.1.3 刚因「两处白名单漂移」打过补丁。

方案：合成一张表＝「紫禁城路由表」：一行一个角色/席位 → 主档 → 备选链 → 约束（独立性/渠道）；另三份从它生成或删。
好处＝用户要的「Excel 表」只有一份，改优先级只改一处；代价＝三个消费方都要改接，改动面大（重级）。

### 14.3 「跨渠道」讲解（用户未听懂项）

场景：48 个档全部从同一个网关（WB 网关 0f0bc352）进入；网关一挂/欠费，全班子上不了班。现有唯一例外＝反审席 DeepSeek（2.1.3）：官方 api.deepseek.com 欠费时，自动改从 WB 网关里的 deepseek 模型出结果。

「跨渠道」＝ 同一模型多条进门口（官方直连／网关 A／网关 B），一条不通走下一档——即用户首次口述的「DeepSeek 渠道 1→2→3」。

| 开法 | 行为 | 风险 |
|---|---|---|
| A 自动 | 系统发现不通自己换 | 可能换到更贵/更慢/额度更小的渠道，换前用户不知情 |
| B 声明后开（推荐） | 只有表里显式写了备选渠道的档才允许换；没写的停 | 需维护声明；渠道＝钱与质量边界，应归用户管 |

### 14.4 编制档案租约制（用户 10-05 方案）

机制：档案带有效期（默认 1 周）→ 派发前懒检查 → 过期不阻断：宽限使用＋并行验证＋续签一周；不设每日定时。与 §11 R4 关系：R4 反驳「硬有效期阻断」，用户方案是「软有效期触发器」（与 R4 修正方向一致）。
