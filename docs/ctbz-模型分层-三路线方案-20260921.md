# ctbz 模型分层：三条路线方案

- 日期：2026-09-21
- 目标：主进程走**官方渠道**（更可靠），子 Agent 走**自建 WB 渠道**（便宜、够用），并让 ctbz 的成本分层规则继续生效
- 配套：`ctbz-迁移dsh-评估-20260921.md`（宿主能力判定）

---

## 0. 结论先行

1. **"主官方 + 子自建"在 dsh 里成立**，而且不需要改 dsh 本体：本次已实测同一次 workflow 内两个 agent 分别落到两条渠道。
2. 三条路的差别不在"能不能"，在**模型分层在哪一层决定**：配置期（路线一）/ 调用期脚本（路线二）/ 进程级调度器（路线三）。
3. 推荐：**路线一起步**（最小、拿角色与工具白名单），把路线二的选型引擎作为它的下一层叠加；路线三只在"每写任务独立 worktree"是硬需求时才上。

| 探针 | 命令/方式 | 结果 |
|---|---|---|

## 2. 三条路线

### 路线一：把角色钉在预设里（配置期静态分层）

**做法**：复制 `standard` preset 为 ctbz 专用 preset；为每个角色挂**一个** `@deepseek-ai/dsh-tool-subagent` 实例：

```yaml
- id: role-reviewer
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: ctbz_reviewer          # 每实例唯一 → 模型看到独立工具
    persona: <角色指令文本>            # 取自 角色清单.json.instructions
    toolFilter: [read, grep, glob]   # 角色工具白名单（宿主侧生效）
    agentOptions: { provider: workbuddy, model: glm-5.3-flash, reasoningEffort: low }
    maxDepth: 1
```

角色 → 模型静态映射建议：`planner/reviewer/explorer/reporter` → WB 最便宜档（如 `glm-5.3-flash`）；`implementer/tester/debugger` → WB 中档（如 `hy4-preview` 或 `deepseek-v4.1-flash`）；主进程 → `deepseek-official/deepseek-flash`（现状）。

| 项 | 内容 |
|---|---|
| 改动面 | 一个 preset 文件 + 一份角色→模型映射表；ctbz 侧 `角色清单.json` 变成 preset 的生成源 |
| 前置 | 复制 preset（`<dshHome>/.agent-presets/ctbz/`）；补声明要用的 WB 模型 |
| 验收 | 8 个角色工具在会话里可见；每个角色只能调白名单内工具（宿主强制）；每次派发的实际模型与映射表一致 |
| 风险 | 未验证 `spawn` 提供方是否支持 `persona`/`toolFilter`（README 称"要求提供方具备"）；preset 变更需新会话 |
| 工作量 | 小（半天级） |
| 收益 | 最小改动拿到"官方主 + 便宜子"；工具白名单从"靠自律"变"宿主执行" |

### 路线二：把选型引擎搬进 workflow（调用期动态分层）

**做法**：把 `pick-profile` 的规则引擎（priority 首中即胜、免费窗口、模型健康账本、命中失败 `--exclude` 下滑下一条）改写为一份 dsh workflow 脚本的选型函数；每次派发调用 `agent(prompt, {provider, model})`，模型由引擎算出并打印决策表。角色靠 prompt 注入（角色指令文本由 `角色清单.json` 生成）。

| 项 | 内容 |
|---|---|
| 改动面 | `pick-profile` + `cost-rules.json` 改写成 workflow 脚本内的纯函数；派发入口从"生成 profile 派发"改为"脚本内 agent() 调用" |
| 前置 | 无（本路线已实测可行） |
| 验收 | 选型决策表可复现；人为制造某模型失败后，脚本按规则下滑到下一条；反审分级（3/4-6/6+）由一个 workflow 完成 |
| 风险 | 工具白名单不再由宿主强制（角色退化为 prompt 约定）；workflow 内的 agent 是一次性的，长任务续跑要用 subagent/teammate 混用 |
| 工作量 | 中（1-2 天） |
| 收益 | **ctbz 成本分层的核心资产完整保留**，且每次调用可换档、可回退、可审计 |

### 路线三：自有调度器 + dsh headless（进程级隔离）

**做法**：ctbz 保留自有 dispatcher（沿用既有 `executor.mjs`/bridge 的状态机、幂等回执、锁设计），通过 dsh 的 headless 任务入口**每次调用起一个独立进程 + 指定模型 + 独立 worktree**（`git worktree add`）；主进程用官方模型，子进程全走 WB。

| 项 | 内容 |
|---|---|
| 改动面 | 重写宿主适配壳；保留 ctbz 的状态机/回执/锁；worktree 隔离自己实现 |
| 前置 | **未验证**：本机 PATH 无 `dsh`，需找到可脚本调用的 headless 入口（app 包内调用或安装 dsh CLI）。headless 能力已确认：一次性任务、`--json` 事件流带 session id、`--session-id` 续聊、退出码 0/1 |
| 验收 | 每个写任务在独立 worktree 独立进程内完成；子进程崩溃不影响主进程；`--json` 事件流可解析出回执与证据 |
| 风险 | 最重；失去 dsh 团队的持久消息与任务板（要自己实现或混用）；进程启动开销 |
| 工作量 | 大（周级） |
| 收益 | **唯一能满足 2.1.0"每写任务独立 worktree + 独立写 owner"并发要求**的路线 |

## 3. 三路线对比

| 维度 | 路线一 预设钉角色 | 路线二 脚本选型 | 路线三 headless 调度 |
|---|---|---|---|
| 模型分层决定点 | 配置期（改 preset） | 调用期（脚本算） | 进程级（dispatcher 钉） |
| 主/子分渠道 | 天然（会话默认官方 + 角色实例 WB） | 天然（脚本显式指定） | 天然 |
| 工具白名单强制 | **宿主强制**（`toolFilter`） | 靠 prompt 约定 | 靠进程内工具面配置 |
| 成本规则（免费窗口/健康账本/回退） | 不支持 | **完整保留** | 完整保留 |
| 独立 worktree | 否 | 否 | **是** |
| 长任务续跑 | teammate 冷恢复 | 需混用 subagent | dispatcher 自己管 |
| 改动量 | 小 | 中 | 大 |
| 主要风险 | `persona`/`toolFilter` 待验 | 角色约束变软 | headless 入口未验证 |

**推荐**：路线一起步（拿角色、工具白名单、最小可跑的"官主 + 便宜子"）→ 叠路线二（把 cost-rules 搬进 workflow，恢复成本分层）→ 2.1.0 的写并发单独评估是否值得上路线三。

## 4. 无论选哪条，都要先做的三件小事

1. **补声明 WB 模型**：把要用的（如 `glm-5.3`、`kimi-k3-1`、`deepseek-v4-pro`）加进 `~/.dsh/settings.yaml` 的 `llm-pi-ai.providers.workbuddy.models`；不声明就在 dsh 里选不到。
2. **开子 Agent 选型白名单**（路线二需要）：
   ```yaml
   subagent-model-selection:
     enabled: true
     allowedModels:
       - { provider: deepseek-official, model: deepseek-flash }
       - { provider: workbuddy, model: glm-5.3-flash }
       - { provider: workbuddy, model: deepseek-v4.1-flash }
   ```
   规则（源码级证据）：`enabled: true` 必须至少一条路由；重复路由报错；白名单在**顶层会话创建时**记录进 Session、子 Session 继承，**之后改设置不影响已开会话**。
3. **主进程钉官方**：`agent-default-model: { provider: deepseek-official, model: deepseek-flash }` 已是当前状态，保持即可。

## 5. 子进程模型名单 v1（用户 2026-09-21 裁定）

**理由**：各家训练方式不同，异构模型能对冲同源偏差 → 讨论/反审/动脑类必须跨阵营取样。

### 5.1 名单（5 个模型 / 4 家提供商，全部实测可用）

| 编号 | 阵营 | provider id | model id | 实测 credit | 定位 |
|---|---|---|---|---|---|
| M1 | DeepSeek | `deepseek-official` | `deepseek-flash` | 官方计费（响应无 credit 字段） | 稳妥档；同时是主进程默认 |
| M2 | 智谱 | `workbuddy` | `glm-5.3-flash` | 0.01 | 主力便宜档 |
| M3 | 腾讯混元 | `workbuddy` | `hy4-preview-f` | 0 | 便宜档（1M 上下文） |
| M4 | 腾讯混元 | `workbuddy` | `hy3` | 0 | 便宜档（192k 上下文） |
| M5 | 月之暗面 | `workbuddy` | `kimi-k2.8-preview` | **0.1** | 贵档，仅讨论/反审类动用 |

实测环境：2026-09-21，同一句提示、`max_tokens=16`；耗时 0.7–2.8s。用户"kimi 贵"的判断由 credit 数据证实（单次为 glm 的 10 倍、混元记 0）。
注意：WB 侧 prompt 有约 **500 token 的固定底噪**（极短提示也报 491–576 prompt tokens）→ 便宜档的价值在长任务里才放大。

### 5.2 任务类型 → 阵营规则

| 任务类型 | 取样规则 | 实际模型组 |
|---|---|---|
| 讨论 / 反审 / 动脑 | **4 家提供商每家至少 1 个** | M1 + M2 +（M3 与 M4 至少一个，齐上则不增阵营只增样本）+ **M5** |
| 开发类（写码、测试、调试、机械执行） | 可排除 M5 | M1 + M2 + M3 + M4（3 家 4 个模型） |

- **反审规模与家数的关系**：4 家齐上即 4 个独立反审 agent，正好落在 ctbz 反审分级的"模块级 4-6"区间下限；框架级 6+ 时按"同家多模型"补（如智谱加 `glm-5.2`、腾讯 M3+M4 同上、月之暗面加 `kimi-k2.6`）。
- **同家两个模型不增加阵营**，只增加样本；判据是"提供商数"不是"模型数"。

### 5.3 落地方式（两条路各自怎么接）

| 路线 | 是否需要改设置 | 写法 |
|---|---|---|
| 路线二（workflow） | **不需要**，已实测 | `agent(prompt, { provider: 'workbuddy', model: 'kimi-k2.8-preview' })`；选型函数按 5.2 表决定传哪一组 |
| 路线一 / subagent 工具 | 需要写 `subagent-model-selection` 白名单，且**只对新会话生效** | 见 `~/Documents/.ctbz/评估/20260921-迁移dsh/settings-子进程模型名单.yaml`（已备好、待应用） |

白名单规则（源码级证据 `dsh-tool-subagent/lib/model-selection-settings.js`）：`enabled: true` 时至少一条路由；重复路由报错；名单在顶层会话创建时记录进 Session 并由子 Session 继承，**之后改设置不影响已开会话**。
