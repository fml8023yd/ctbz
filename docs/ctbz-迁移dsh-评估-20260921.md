## 0.5 原始两问的直接答案（2026-09-21 追加）

### 问一：ctbz 能不能在 dsh 上用？

**能，而且今天就能跑最小闭环。** 分三态：

| 态 | 内容 | 证据 |
|---|---|---|
| ✅ 今天就能用 | SKILL.md 主协议（本会话已作为 skill 加载并生效）、脚本（知识库/意见箱/settings/模型健康）、看板（纯 node http，18921）、发布链、worktree、判型/四扇门/验收表等纯文本协议、按调用点分派子 agent（已实测跨两条渠道） | 本会话实跑 |
| 🟡 能用但要先做小事 | 补 `~/.dsh/AGENTS.md`（现缺）；子 agent 按调用点选模型（subagent 工具需写 `subagent-model-selection` 白名单，只对新会话生效）；定时任务改挂 launchd；workspace 状态目录由 `.zcode/` 改自有 `.ctbz-record` | §3 各条 |
| 🔴 用不了（宿主无此概念） | profile 注册链（prepare/activate、doctor、render-agents、discover-config、validate-team）、104 个 profile、modelRef 编码、`~/.zcode` 凭据与发现路径 | §4.1/4.2 |

一句话：**"ctbz 作为协议 + 技能 + 脚本"完全能用；"ctbz 作为宿主 agent 注册体系"用不了。**

### 问二：ctbz 能否借鉴/融合 dsh 的功能（如 teams）？

**能，而且应该是双向的。** 分三类：

| 类别 | dsh 件 | ctbz 现状 | 融合方式 |
|---|---|---|---|
| 接管运行时 | teams（持久消息、任务板 CAS/依赖/owner、冷恢复）、goal 续轮、jobs、present、输出溢出 | 靠协议自觉 + `team-state` 文件 | **运行时交给 dsh；权威台账仍归 ctbz**（checkpoint/回执/验收表不丢） |
| 借来增强 | workflow（多模型异构 + 结构化返回）、hook 桥（`PreToolUse` 可阻断/ask）、plugin 通道（注册原生工具与提示词段） | 缺机械门禁与结构化多模型反审 | 四扇门上 hook 真锁；反审分级＝一次 workflow（4 家阵营）；team-state/知识库/看板可升级为 bundle 原生工具 |
| ctbz 反向供给 | dsh teams **无审批/提问入口、owner 不自动释放、共享工作区、teammate 不能选模型** | 有判型三问、四扇门、反审打回闭环、验收表、write-set/worktree、成本选型、知识库与看板审批 | dsh teams 补上这套治理内核才完整 |

**结论一句话**：不是"把 ctbz 迁到 dsh"，而是 **dsh 出骨架（运行时可靠性）、ctbz 出内核（决策与验收制度）**；teams 接管 ctbz 里"靠自觉"的那一半，ctbz 补上 teams 里"没人管治理"的那一半。

## 4. 🔴 必须重做

### 4.1 agent profile 注册链整链退役（大）
`scripts/initialize`（prepare/activate）、`scripts/doctor --activate`、`render-agents`、`discover-config`、`validate-team`、`assets/team-config.schema.json` 全部围绕"往 `~/.zcode/agents/` 生成 agent profile、再由宿主加载"这一机制。
- 证据：`references/configuration.md:11-19`；`scripts/initialize:21,33,137`；`scripts/lib/paths.mjs:5-6`；`assets/team-config.schema.json:3-4`。
- dsh 没有这套注册概念：它的"角色"落点是 **agent preset**（每会话一套组装：工具 + 提示词段落 + skill），来源=随包 preset + `Config.roots` + `<dshHome>/.agent-presets`，创作方式=复制已有 preset 改文件；subagent 加入父方组装。（`dsh-agent-presets/README.zh.md`）
- 处置建议：**整链退役**，需要"多角色"时改用 preset（或第 4.4 的编排路径），不要试图把 profile 注册搬到 dsh。

### 4.2 provider/凭据发现链换源（中-大）
`scripts/doctor:395` 要求 `--config` 指向含 `provider`/`providers` + `options.apiKey` 的 ZCode config；`scripts/lib/model-ref.mjs:1,16-21` 负责 ZCode profile 的 `custom:<providerId>:<modelId>` 编码。
- dsh 侧模型/provider 由 `~/.dsh/settings.yaml` 声明（`llm-deepseek`、`llm-pi-ai` 的 `providers` + `models`），凭据在 `~/.dsh/.credentials.yaml`。
- 处置建议：重写为 dsh 侧的 provider/model 枚举与凭据存在性检查；`model-ref.mjs` 的编码逻辑整体作废。

### 4.3 角色×模型：能力还在，选型机制换了（设计级；本节已按 2026-09-21 二次取证更正）

**更正说明**：初版写成"无法按角色落地"过于绝对。二次取证后：**按角色钉模型可以做到，且比 ZCode 更灵活；真正丢失的是"派发前的确定性选型引擎"。**

三条通道（按能力从粗到细）：

| 通道 | 能否定角色 | 能否定模型 | 证据 |
|---|---|---|---|
| `spawn_teammate`（团队包） | 只能靠初始任务文字描述 | **不能**，无 model 参数 | `dsh-experimental-tool-agent-team/README.zh.md`；本会话工具契约 |
| `subagent` 工具**实例** | **能**：`persona`（每子 agent 独立人格）+ `toolFilter`（每子 agent 独立的全局工具限制） | **能（配置期钉）**：`agentOptions` 的 `provider`/`model`/`reasoningEffort`/`maxTokens` 默认值；一个 preset 可挂多个实例，`toolName` 每实例唯一 | `dsh-tool-subagent/README.zh.md:40-70` |
| `subagent` 工具调用 | 同上 | **能（调用期由父模型选）**：开 `modelSelectionSettings: true` 后公开 `provider`/`model`/`reasoning_effort` 与 `list_subagent_models`；路由白名单在顶层会话创建时从宿主 `subagent-model-selection` 记录、之后编辑设置不再改变 | 同上 |
| `workflow` 的 `agent(prompt, {provider, model})` | 靠 prompt | **能（调用期由脚本钉）**，本会话已实测生效 | 本会话工具契约 |

因此映射关系是：**一个角色 = 一个 subagent 工具实例**（`persona` + `toolFilter` + `agentOptions` 默认模型），这恰好替掉 ZCode 用 profile 干的事；代价是 ZCode 的"8 角色 × N 模型 = 104 profile 全量静态生成"要变成"预设里声明若干实例"。

**真正丢失的是选型环节本身**：ZCode 的模型选择是**派发前由父进程跑确定性规则引擎**（`pick-profile` + `cost-rules.json`：priority 首中即胜、免费窗口、模型健康账本、命中失败带 `--exclude` 自动下滑），可审计、可复现；dsh 侧是**父模型自主判断**，宿主不提供确定性路由与失败回退（`list_subagent_models` 只给建议，目录成员资格不构成限制）。
- **已验证（2026-09-21 二次取证）**：`spawn` 后端声明支持**全部**启动期能力 `agentOptions` / `outputSchema` / `depthLimit` / **`toolFilter`** / **`persona`**；实现为 `childCtx.tools.restrict(composition.toolFilter)` 与 `childCtx.systemPrompt.section({name:"deployment:persona-prefix", text:composition.persona})`。证据：`@deepseek-ai/dsh-subagent-spawn-in-process/lib/index.js`（`capabilities = { agentOptions:true, outputSchema:true, depthLimit:true, toolFilter:true, persona:true }`）、`@deepseek-ai/dsh-subagent/lib/index.js:551-556`。→ **只读角色（planner/reviewer/explorer/reporter）的工具白名单可由宿主强制**，路线一成立。
- 处置建议：`pick-profile` 的**决策函数**是资产，原样保留；把宿主从"生成 profile 供宿主加载"换成"preset 里声明角色工具实例 + workflow 脚本里做调用期选型"。成本分档的落点从"角色"移到"调用点"，规则引擎本身不丢。

### 4.4 每写任务独立 worktree 的并发模型要重设（设计级）
- ctbz 2.1.0 方案要求"每个写任务使用独立 worktree、独立分支；同一可编译单元一个写 owner"（`源码/docs/ctbz-2.1.0-激进并发与质量闭环技术方案.md:15-21`）。
- dsh 团队包明确**不支持独立工作目录**："当 teammate 需要独立工作目录、多个进程需要协调同一支团队、或任务 owner 需要自动释放时，请不要选择——这些都不受支持"（`dsh-experimental-agent-team/README.zh.md`）。团队上限 `maxMembers 16`、`maxTasks 256`、单成员待处理消息 64、单条消息 64KiB。
- 处置建议：二选一——① 写并发收敛为 1（其余并行 readonly），worktree 仅用于人工集成；② 用 `workflow`/外部 headless 把每个 writer 起成**独立进程**，在各自 worktree 里跑，回执落盘（沿用既有 executor 的状态机设计）。

### 4.5 不注册会损失什么（逐项算账，2026-09-21）

注册链（`discover-config` → `render-agents` → `prepare` → `doctor --activate` → `activate` → `select`）实际买到的 10 样东西，逐项对照：

| # | 注册链买到什么 | 不注册后的状态 | 判定 |
|---|---|---|---|
| 1 | 角色可派发（8 角色 × N 模型 profile） | preset 里声明 subagent 实例即可 | ✅ 不损失（换写法） |
| 2 | 工具白名单（只读角色） | `toolFilter` → `childCtx.tools.restrict()`，**宿主强制** | ✅ 不损失（已取证） |
| 3 | 角色人格/指令 | `persona` → 子 agent 的 systemPrompt 段 | ✅ 不损失 |
| 4 | 模型绑定 | `agentOptions.provider/model`（实例默认）+ 调用期覆盖 | ✅ 不损失（更灵活） |
| 5 | **派发前统一预检**（凭据/模型是否在编/安装漂移） | dsh 无"派发前体检"这一环节 | ⚠️ **真损失**，需自建（约 50 行）或让失败暴露 |
| 6 | **按角色自动过滤冷却/限额模型** | dsh 无宿主钩子 | ⚠️ **真损失**（健康账本本身属 🟡，可挂进选型函数补回） |
| 7 | 回执自动可推"哪个模型跑的"（profile 名编码模型） | 需显式把 provider/model 写进台账 | ⚠️ 小损失（记录义务变显式） |
| 8 | 跨会话/跨机一致分发 | 改为 preset 目录分发（同样可 git 管理），但 preset 只在**新会话**组装 | ⚠️ 分发方式变了，不算丢失 |
| 9 | **指纹/漂移校验**（registryHash / installRoot / lock） | dsh 有自己的 bundle/patch 校验，但不是 ctbz 这套自定义的 | ⚠️ **真损失**；可保留宿主无关的 `dependencies.lock` + 发布检查，只砍"宿主加载名单"那半 |
| 10 | 激活登记（activeSessions / 已初始化.txt） | dsh 用 sessionId + goal 续轮 + 队友冷恢复 | ✅ 不需要（能力更强） |

**外加一项必须诚实说的实质代价：角色从"宿主一等实体"降级为"配置条目"。**
- ZCode：`reviewer` 是宿主认识的一个 agent——可点名、可在派发时选择、roster 可见、profile 名自带模型编码。
- dsh：`spawn_teammate` **没有角色类型**（只收名字/描述/任务）；角色只能靠 ① preset 里预声明的固定 subagent 实例，或 ② prompt/任务文字表达。
- 影响：角色数量与组合要**配置期定死**；运行时"临时新增一个角色"不如 ZCode 自然（要改 preset 并新开会话）。

**净结论**：不注册 = 丢掉「预检 / 冷却过滤 / 指纹校验」三件外围保障 + 角色降级为配置条目；**角色能力本身（人格、工具白名单、模型绑定）一项不丢**。
**代价**：三件外围保障合起来约一个 50–100 行的选型/预检脚本（放在 workflow 脚本里天然有位置），角色声明约一次 preset 编写——远低于维护 104 个 profile 加一条注册链。

→ **四项损失的补齐方案见** `ctbz-迁移损失四项-补齐方案-20260921.md`（结论：四项全部可解，其中角色降级可完全逆转，收敛形态是把 ctbz 做成 dsh bundle 插件）。

## 7. 两条进阶路径（本次不实施，仅登记）

### 7.1 ctbz 可升级为 dsh「组合包（bundle）」而非只做 skill（中-大）
dsh 的插件通道比 skill 深一层：插件通过 `ctx.skills.register`、`ctx.systemPrompt.section`、ToolSchema 提供方注册 **skill / 提示词段落 / 原生工具**；安装 spec 支持 npm 包、git、本地绝对路径、tarball；成为 bundle 需在自己 `package.json` 声明 `dsh.bundle.patch`，启用即把它加进 profile 的 `dsh.profile.bundles`。
- 证据：`dsh-plugin-manager/README.zh.md`、`dsh-plugin-manager/lib/types/{install-spec.js,operations.js,patch.js}`、`dsh-skill/README.zh.md`、`dsh-system-prompt/README.zh.md`、`dsh-app-boot/README.zh.md`。
- 限制：`plugin_manager` 每个操作要求 `danger-full-access` 或本次调用批准；替换已有包后需重启进程才加载新 JS；管理器不能改其他 profile、不能编辑 agent 预设组合。
- 收益：`team-state`/`知识库`/`看板` 可从"外部脚本"升级为宿主内原生工具 + 提示词段落，减少"协议靠自觉"的损耗。

### 7.2 dsh Web GUI 已自带团队面板，与 ctbz 看板分工（小）
Web 侧开 Agent Teams 层后（`dsh plugin --profile web add @deepseek-ai/dsh-experimental-agent-team-profile` 及其 web 层；默认关闭），GUI 提供两块可视化：**roster**（name / status / model / diagnostics）与**共享任务板**（owner / blocker / readiness / 写入范围提示与重叠警告），人类可在面板上建/改/分配/完成/重开/删除任务。**没有审批或提问入口**，panel 不能 spawn/rename/delete/interrupt teammate，且只在打开、显式刷新与变更后刷新（无实时订阅、无 mailbox 时间线）。
- 证据：`dsh-experimental-client-ui-agent-team/README.zh.md`、`dsh-experimental-agent-team-web-profile/{README.zh.md,cordis.patch.yml,package.json}`、`.../lib/client.js`。
- 分工建议：运行时协作（谁在跑、谁卡住、任务归属）交给 dsh 面板；**项目台账、裁决与审批仍归 ctbz 看板**（dsh 面板无审批入口，无法承接 ctbz 的 questions/checkpoint 协议）。
